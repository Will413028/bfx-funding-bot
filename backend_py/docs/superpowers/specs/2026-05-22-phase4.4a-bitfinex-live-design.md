# Phase 4.4a — Bitfinex Live Event Infrastructure Design

## 1. Context

### 1.1 Recap

Phase 4.3 ship `dfece968` 既有：DomainEventBus、Executor middleware chain (Heartbeat / ReservationEmitting / TransientRetry)、dual-counter ledger (_reserved + _realized)、`OrderFilled` 含 Optional `credit_id` 預留 4.4 populate、`ReservationReleased.reason` 含 4 個 enum 值 + 4.4 WS handler refinement hook。

Phase 4.4 prework ship `9261f3f` 既有：boot smoke L2 deploy gate、admin `/admin/smoke-test` endpoint、SmokeRunner core、`?mode=paper|live` query param hook (live mode 4.4b 接)。

### 1.2 4.4 拆分

Phase 4.4 完整 scope 為 BitfinexLive executor + WS event 處理 + L2 guards + paper→live cutover。Single phase 14-task subagent-driven scale 過 4.3 (15 task) 一截，因此拆 2 phase：

- **4.4a (此 spec)**：WS event 基礎建設 — auth WS client、live executor、OfferRegistry FSM、WS dispatcher。Paper executor 仍 default、prod 仍 paper-mode deploy。
- **4.4b (待寫)**：L2 guards 接 `ledger.realized_exposure()`、paper→live config flag、smoke endpoint live mode、production canary verify、reconcile-on-reconnect。

4.4a → deploy paper-mode 驗 module wiring 不破壞既有 path → 4.4b cutover 切 live。

### 1.3 Pre-prod 重構窗口

系統未上線、Axiom 既有 row 量有限、單 process / 單 tenant。pre-prod 是把 best-practice 烤進架構的最後機會。本 spec 將 Stripe-grade event-sourcing + functional-core-imperative-shell + hexagonal-strict 三項 baked in，避免 Phase 5+ multi-tenant / multi-venue 翻新債。

## 4. System Properties (Invariants)

4.4a 後系統保證下列 5 條 invariant；任一 future change 須 preserve。Spec self-review checklist 之一。

### G1 — At-least-once + Idempotent = Exactly-once-effect

Every event publication path 為 at-least-once（WS / REST / bus 可能 retry）。Every consumer (Ledger / OfferRegistry / AxiomSink) idempotent via `(venue_offer_id, venue_seq)` dedup set。Net effect on projection state = exactly-once。

**Mechanism**：
- Ledger `_processed_releases: set[(venue_offer_id, venue_seq | None)]` 與 `_processed_fills` 同
- OfferRegistry FSM 對 RELEASED state 重複 incoming → no-op
- AxiomSink emit by event identity，row 重複時 Axiom 端 timestamp-based dedup（既有）

### G2 — Read-your-writes

After `bus.publish(X)` returns, all current subscribers have observed X. Guaranteed by `await asyncio.gather(*handlers, return_exceptions=True)` in DomainEventBus.publish。

**測試**：`test_g2_read_your_writes.py` — publish 後立即 read ledger / registry state 必看到 X effect。

### G3 — Deterministic replay

For any event log `[E1, ..., En]`, replay reproduces identical projection state. Guaranteed by:
- (a) Pure `transition()` functions — no random / no clock / no I/O
- (b) Sort by `(occurred_at_ms, event_seq)` 完全 total ordering
- (c) Explicit upcaster chain handles schema evolution

**禁**：projection 路徑 `uuid4()` / `time.time()` / 任何非 deterministic 操作。fill_tracker 既有 `uuid4()` for signal_correlation_id (line 175) 為已知 bug，4.4a 必 fix。

**測試**：`test_g3_deterministic_replay.py` — seed Axiom with N events → replay 兩次 → ledger / registry 完全 identical。

### G4 — End-to-end backpressure

WS dispatcher bounded queue (max=10_000) → 80% fill 觸 DEGRADED + WARN → 100% fill 觸 block put → backpressure 到 WS recv → Bitfinex 端 venue push slow。No silent data loss。

**Observability**：每 30s emit `queue_depth` HealthCheck row。

### G5 — Time travel

`replay_from_axiom(up_to_ms=T)` reconstructs projection state at any point T. 4.4a 預埋 `up_to_ms` parameter（real `_AxiomQueryAdapter` ship 後 actually fetch；4.4a stub 仍 no-op）。

**用途**：forensic debugging / audit / pre-cutover state verification。

### 5.2 daemon._run TaskGroup wiring 順序

```
1. ledger.replay_from_axiom()                 (4.3 既有)
2. offer_registry.replay_from_axiom()         (NEW · cold-start projection)
3. bus.subscribe(handlers)
   - ReservationClaimed → ledger / offer_registry / axiom_sink
   - OrderFilled        → ledger / offer_registry / axiom_sink
   - ReservationReleased → ledger / offer_registry / axiom_sink (defensive comment)
   - CancelRequested    → axiom_sink / dispatcher
4. TaskGroup:
   - if BFX_WS_CLIENT_ENABLED:
       auth_ws.run(stop_event)
       ws_dispatcher.run(stop_event)
   - if BFX_FILL_TRACKER_ENABLED:
       fill_tracker.poll_loop(stop_event)
   - strategy decision loop                   (既有)
   - smoke_runner / probe                     (既有)
5. (on shutdown) smoke_runner.aclose()        (NEW helper · refactor bundled)
```

4.4a default `BFX_EXECUTOR=paper` / `BFX_WS_CLIENT_ENABLED=false` / `BFX_FILL_TRACKER_ENABLED=false`，所有新 task 不啟動 — paper-preserving deploy。

### 5.3 Supervision strategy

asyncio TaskGroup "one-for-all" — 任一 task raise `InvariantViolation` 或未 catch `AuthError` → 全 cancel → daemon 退 → Koyeb auto-restart (~30-60s)。

理由：Trading 系統 partial-functioning 風險不對稱（half-alive ws 漏 fcn → exposure stuck），全停 + restart 比 half-functional 安全。`TransientError` / `PermanentError` 各 module 內部處理不 escalate。

## 6. Components

### 6.1 `external/bitfinex/auth_ws.py` · BitfinexAuthWSClient

**Purpose**：Authenticated Bitfinex WS connection (user channels `fcn/fcu/foc/wu/ws/ou/on/oc`) → typed dataclass stream。純 venue I/O。

**Pure functions**：
- `build_auth_payload(api_key, api_secret, nonce_ms) -> dict`：HMAC-SHA384 sign per Bitfinex API docs；nonce 從外部 inject (test 可控)
- `parse_frame(raw) -> BfxWSEvent | None`：raw JSON → discriminated union `FcnEvent | FcuEvent | FocEvent | AuthAck | Heartbeat | ChannelInfo | Unknown`；解析失敗 return None + log warn，**不 raise**

**Imperative shell** `BitfinexAuthWSClient`：
- `__init__(*, creds: Credentials, url, hb_timeout_s=30, nonce_provider=None, on_disconnect=None)`
- `async def events() -> AsyncIterator[BfxWSEvent]`：對外唯一 async iterator
- `async def close()`
- 內部 reconnect with exponential backoff (mirror 既有 `BitfinexWSClient` candles：1, 2, 4, ..., 60s cap)；heartbeat watchdog；reconnect_count_last_hour 觀測 method

**Typed events (`BfxWSEvent` union)**：

```python
@dataclass(frozen=True, slots=True)
class FcnEvent:                       # FUNDING CREDIT NEW
    credit_id: int
    symbol: str
    side: int
    mts_create: int                   # bitemporal occurred_at
    mts_update: int
    amount: Decimal
    rate: float
    period_days: int
    offer_id_meta: int | None         # cross-map to our cid (depending on Bitfinex schema)
    raw_seq: int | None               # WS SEQ for idempotency
    raw: list                         # 完整原 payload 留 audit

# 類似 FcuEvent / FocEvent / AuthAck / Heartbeat / ChannelInfo / Unknown
# FocEvent 額外 status: str ("EXECUTED @ ..." / "CANCELED" / "EXPIRED")
```

**Invariants**：
- 不持 mutable cross-session state (reconnect 後 rebuild)
- Frame 解析錯誤 → log + None；連線 not affected
- Auth 失敗 boot fail-fast；runtime auth invalidate → DEGRADED + retry 5 次 escalate `AuthError`

**Tests**：
- Unit (90%)：`parse_frame` hypothesis property test 對 recorded fixture
- Integration：in-process fake aiohttp WS server emit recorded fcn/fcu/foc → `async for ev in client.events()` assertion

### 6.2 `external/bitfinex/ws_dispatcher.py` · BitfinexLiveWSDispatcher

**Purpose**：consume `BitfinexAuthWSClient.events()` + 查 OfferRegistry + 查 `recent_cancels` → pure `translate_bfx_event` → publish DomainEvent。ACL 核心點。

**Pure function**：

```python
def translate_bfx_event(
    bfx_event: BfxWSEvent,
    registry_snapshot: dict[str, ClaimRecord],
    recent_cancels: dict[str, int],   # venue_offer_id → requested_at_ms (60s TTL)
    now_ms: int,
) -> tuple[list[DomainEvent], list[RegistryMutation], list[DiagnosticLog]]:
    """Pure mapping logic. 無 I/O / 無 random / 無 clock dependence (now_ms inject)."""
```

對應表：

| BfxWSEvent | Registry state | Emit DomainEvent | Mutation |
|---|---|---|---|
| FcnEvent | CLAIMED | `OrderFilled(credit_id, venue_seq, occurred_at_ms=fcn.mts_create)` | `state=RELEASED` |
| FcnEvent | not found | `[]` + diag "stage in OOO buffer" | shell 之 staging buffer (200ms TTL) |
| FocEvent EXECUTED | CLAIMED | `[]` + diag "foc EXECUTED redundant — fcn handled" | no-op |
| FocEvent CANCELED | CLAIMED + venue_offer_id in recent_cancels (≤5s) | `ReservationReleased(reason=user_cancel)` | `state=RELEASED` |
| FocEvent CANCELED | CLAIMED + 無 recent_cancels match | `ReservationReleased(reason=venue_cancel)` | `state=RELEASED` |
| FocEvent EXPIRED | CLAIMED | `ReservationReleased(reason=expired)` | `state=RELEASED` |
| FocEvent (任一 status) | RELEASED | `[]` (idempotent dedup) | no-op + diag |
| FcuEvent (credit update) | RELEASED | `[]` (rate updates not modeled 4.4a) | no-op |
| Unknown | any | `[]` + diag "unknown event variant" | no-op |

**Imperative shell** `BitfinexLiveWSDispatcher`：
- `__init__(*, ws_client, registry, bus, axiom, clock, queue_max=10_000)`
- `async def run(stop_event)`：bounded queue 抓 events、每 tick 跑 pure fn → `registry.apply(mutation)` 各個 → `await bus.publish(event)` 各個 → all errors log + continue
- 每 30s emit `queue_depth` health metric
- 80% queue depth → HealthProbe DEGRADED + WARN row；100% → block put + ERROR row
- Staging buffer TTL cleanup task (每 50ms check) — 超 200ms 仍未 drain → drop entry + ERROR row
- Subscribe `CancelRequested` 維護 `_recent_cancels: dict[venue_offer_id, ts_ms]` (60s TTL)

**Invariants**：
- Translate fn 是 pure — replay 完全 deterministic
- Staging buffer 是 implementation detail (4.4b 升級為 OfferLifecycleSaga)
- Dispatcher 不對 venue / bus retry — pure forwarder

**Tests**：
- Unit (~95%)：hypothesis 對 `translate_bfx_event` 全 BfxWSEvent variant × registry state × recent_cancels
- Integration：fake WS server emit recorded session → ledger / axiom_sink react assertion

### 6.3 `external/bitfinex/live_executor.py` · BitfinexLiveExecutor

**Purpose**：實作 `ExecutorPort.submit(decision, ctx) -> SubmittedOrder`。純 REST。對 `POST /v2/auth/w/funding/offer/submit` 下 offer、回 `SubmittedOrder(status="submitted", venue_offer_id from response)`。不知 WS 存在。

**Pure functions**：
- `build_offer_payload(decision, ctx, cid) -> dict`
- `parse_offer_response(http_response) -> SubmittedOrder`
- `sign_request(body, nonce, api_secret, path) -> dict[str, str]` (與 auth_ws 共用底層 signer)

**Imperative shell** `BitfinexLiveExecutor`：
- `__init__(*, http, rate_limiter, axiom, bus, phase, strategy, cell, nonce_provider, date_provider)`
- `async def submit(decision, ctx) -> SubmittedOrder`：
  - `cid = generate_cid(decision.signal_correlation_id, date_provider())` — CC2 capture-once
  - `payload = build_offer_payload(...)` (pure)
  - `rate_limiter.acquire()`
  - HTTP POST (transient_retry middleware 既有)
  - `parse_offer_response(resp)` → SubmittedOrder
- `async def cancel(venue_offer_id, signal_correlation_id, account_id)`：
  - POST `/v2/auth/w/funding/offer/cancel`
  - **NEW**：`await bus.publish(CancelRequested(venue_offer_id, requested_at_ms=now, signal_correlation_id, account_id))`
  - **不**持本地 `_pending_cancels` dict — 改 dispatcher subscribe CancelRequested 維護 `_recent_cancels`

**Invariants**：
- Returns `status="submitted"` 不是 `"filled"` (WS fcn 後續決定)
- `status="failed"` → ReservationEmittingMiddleware skip publish (既有 I3-EM)
- Cid daily idempotency 經 Bitfinex 端保證 (既有 4.3 design)
- 不對既有 events subscribe / 不對 registry 知情 — pure REST

**Tests**：
- Unit：`build_offer_payload` / `parse_offer_response` / `sign_request` 100% coverage
- Integration：httpx MockTransport 模擬 Bitfinex response → assertion + bus.publish(CancelRequested) 驗

### 6.4 `modules/execution/registry_offers.py` · OfferRegistry

**Purpose**：in-memory FSM projection of bus events。Subscribe `ReservationClaimed / OrderFilled / ReservationReleased` 自建 `dict[venue_offer_id, ClaimRecord]`。Dispatcher 查它 lookup correlation_id / size_usdt 等。

**Pure types + function**：

```python
class RegistryState(Enum):
    PENDING = "pending"    # 4.4b reserved · 4.4a 不使用 (新 ClaimRecord 直接 CLAIMED)
    CLAIMED = "claimed"
    RELEASED = "released"

@dataclass(frozen=True, slots=True)
class ClaimRecord:
    venue_offer_id: str
    cid: int
    signal_correlation_id: UUID
    size_usdt: Decimal
    account_id: str
    state: RegistryState
    occurred_at_ms: int
    last_updated_ms: int

@dataclass(frozen=True, slots=True)
class RegistryMutation:
    venue_offer_id: str
    new_state: RegistryState
    occurred_at_ms: int

def transition(
    snapshot: dict[str, ClaimRecord],
    incoming: DomainEvent,
    now_ms: int,
) -> tuple[dict[str, ClaimRecord], list[DiagnosticLog]]:
    """Pure FSM. Snapshot → new snapshot. Hypothesis 全狀態空間覆蓋."""
```

對應表：

| Incoming event | Current state | New state | Note |
|---|---|---|---|
| ReservationClaimed | not in registry | CLAIMED | 新增 ClaimRecord |
| ReservationClaimed | already CLAIMED | unchanged | dedup by venue_offer_id |
| OrderFilled | CLAIMED | RELEASED | normal |
| OrderFilled | not in registry | unchanged + diag "fcn before claimed — should stage" | dispatcher 端 staging buffer |
| OrderFilled | RELEASED | unchanged | idempotent |
| ReservationReleased | CLAIMED | RELEASED | normal |
| ReservationReleased | RELEASED | unchanged | idempotent |
| ReservationReleased | not in registry | unchanged + diag warn | fill_tracker 不應走到此 (registry-aware dedup) |

**Imperative shell** `OfferRegistry`：
- `__init__(*, axiom_query, clock=lambda: int(time.time()*1000))`
- `async def replay_from_axiom(up_to_ms=None)` — boot 時取 ReservationClaimed/OrderFilled/ReservationReleased rows 經 upcaster_chain → sort by `(occurred_at_ms, event_seq)` → 依序套 `transition()` (4.4a stub 仍 return [] 直到 real query adapter ship)
- `def snapshot() -> dict[str, ClaimRecord]` — immutable view (dict copy)
- `async def handle(event)` — bus subscriber callback：snapshot → transition → atomic swap
- `def cleanup_terminal(older_than_ms)` — RELEASED state 超過 24hr 移除 (memory cap)

**Invariants**：
- 任一時刻 dict 至多 1 ClaimRecord per venue_offer_id
- 不持 history (pure projection；history 在 Axiom)
- Replay determinism：相同 row set → identical final snapshot

**Tests**：
- Unit (~99%)：`transition` hypothesis full state × event types
- Integration：real bus → 3 event sequence → snapshot 驗

### 6.6 `modules/execution/event_upcasters.py` (NEW) — schema migration framework

```python
def upcast_v1_to_v2(row: dict) -> dict:
    """4.3 row → 4.4a row: 加 venue_seq / event_seq / occurred_at_ms / recorded_at_ms = None"""
    return {**row,
            "venue_seq": row.get("venue_seq"),
            "event_seq": row.get("event_seq"),
            "occurred_at_ms": row.get("occurred_at_ms"),
            "recorded_at_ms": row.get("recorded_at_ms")}

UPCASTER_CHAIN: list[Callable[[dict], dict]] = [
    upcast_v1_to_v2,
]

def upcast_row(row: dict) -> dict:
    for upcaster in UPCASTER_CHAIN:
        row = upcaster(row)
    return row
```

**Schema version 約定**（events.py top of file `__SCHEMA_VERSION__ = 2`）：新 field 加進 events.py + upcaster chain + 單元 test 同步；既有 row schema 永不破壞 (field remove forbidden)。

### 7.5 Cold start replay — process restart

```
daemon._run boot:
  1. ledger.replay_from_axiom():
       query: rows event_type ∈ {RESERVATION_CLAIMED, ORDER_FILL, RESERVATION_RELEASED}
       upcast_row(row) for each → parse_event(row)
       sort by (occurred_at_ms, event_seq) ← deterministic
       for event: call ledger.handle_* directly (skip bus.publish)
       終態：_reserved + _realized 重建到 process down 前

  2. offer_registry.replay_from_axiom():
       same row set, same sort
       for event: pure transition(snapshot, event) iteration
       終態：registry dict 重建含所有歷史 ClaimRecord (含 RELEASED state — Axiom log 永留)
       post-replay → offer_registry.cleanup_terminal(older_than_ms=24hr) 刪過老 RELEASED 釋記憶體

  3. bus.subscribe (live path begin)
  4. TaskGroup launch
```

**Determinism**：
- Optional bitemporal/seq fields 提供 total ordering（4.3 既有 row 退 fallback ordering，內部 dedup 仍有效）
- `transition()` 無 random / clock → replay N 次得 identical state

**4.4a Gap**：`_AxiomQueryAdapter` 4.3 stub 返 `[]` → `replay_from_axiom` actual no-op。
- 4.4a deploy 仍 paper-mode，路徑不觸發
- 4.4b cutover 前必 ship real `_AxiomQueryAdapter`（separate ADR 已 Followup 標）

## 8. Error Handling

### 8.1 Error taxonomy

```python
# modules/execution/errors.py · NEW (extends 既有)
class ExecutionError(Exception): ...
class TransientError(ExecutionError):       # network / timeout / rate-limit
class PermanentError(ExecutionError):       # business reject
class InvariantViolation(ExecutionError):   # internal inconsistency → fail-fast
class AuthError(ExecutionError):            # credential / sig
```

每 module 拋 error 走此分類，**禁 string match**。

### 8.2 Per-module policy

**BitfinexAuthWSClient**：
- `websockets.ConnectionClosed` → reconnect exp backoff；on_disconnect hook
- Heartbeat timeout → force close + reconnect
- Auth ack 5s timeout → boot fail-fast；runtime 5 連續 → DEGRADED + escalate `InvariantViolation`
- Parse error → log + skip frame；連線不影響
- Send-side error (subscribe reject) → boot fail-fast (`PermanentError`)

**BitfinexLiveWSDispatcher**：
- Unknown BfxWSEvent → diag + continue
- Invalid registry transition → pure fn 已 no-op + diag
- `bus.publish` raise → log critical + continue (single frame fail 不停 dispatcher)
- Queue 80%/100% → DEGRADED / backpressure
- Staging buffer TTL drop → ERROR

**BitfinexLiveExecutor** (借 4.3 transient_retry middleware)：
- 429 → rate limit backoff + retry
- 5xx / timeout → exp retry up to 3
- 4xx (除 429) → PermanentError → status="failed"
- 401/403 → AuthError → runtime DEGRADED + escalate
- Response schema malformed → InvariantViolation fail-fast

**OfferRegistry**：
- Unknown event type → diag (no mutation)
- Concurrent handle race (4.4a 純 asyncio single-writer 不需 lock)
- `replay_from_axiom` row 不認 → upcaster chain raise InvariantViolation

**fill_tracker** (既有 4.2 + 4.4a 加 registry-aware dedup)：
- Atomic poll fail → consecutive_failures++、last_state preserve、3 次連續 → DEGRADED
- paper_ prefix → InvariantViolation (CC4 既有)
- registry snapshot non-CLAIMED → dedup skip
- registry snapshot empty → log warn, skip

**Ledger**：
- Duplicate `(venue_offer_id, venue_seq)` → log debug + skip
- `_reserved -= size` < 0 → floor 0 + warn (既有)
- handler raise → bus gather isolate

- `PermanentError` → 內部 log + skip / mark unhealthy

## 10. Open Questions (spec self-review 候選)

**Q1**：Bitfinex `fcn` payload 的 `offer_id_meta` field 真實位置 + 是否 100% 出現？4.4a 假設可 cross-map 回 `venue_offer_id`，若實際 None 時需 fallback strategy。
- **Mitigation**：4.4a 實作前先 manual call Bitfinex test account 抓 fcn raw payload；若 offer_id_meta 缺失，registry lookup 改用 credit_id ↔ venue_offer_id 中介索引（OfferRegistry 加 `credit_id_index: dict[int, str]`）。

**Q2**：CancelRequested event 是否需 emit Axiom row？
- **Decision**：Yes — audit trail + replay determinism 都需要。AxiomSink 加 CancelRequested handler，Axiom 端新 event_type `CANCEL_REQUESTED`。

**Q3**：OfferRegistry `cleanup_terminal` (24hr 移除 RELEASED) 是否與 funding offer 期限 (30 天) 衝突？
- **Answer**：不衝突。Offer 在 30 天內被撮合或取消後就 RELEASED → 進 24hr cleanup 窗口。30 天是 venue 端 offer 存活上限、registry 24hr 是 RELEASED state cleanup（offer 已生命結束）。

**Q4**：`venue_seq` 在 BitfinexLiveExecutor REST submit response 是否取得到？
- **Answer**：不需要。venue_seq 僅 WS event 有（Bitfinex SEQ field）。ReservationClaimed (from REST submit) 留 venue_seq=None 是 OK 的，因 Ledger dedup 對 `(venue_offer_id, None)` key 在 process lifetime 內仍唯一（4.3 既有 path 無 dup）。

**Q5**：Tier 1 baked Pydantic v2 migration 是否一併做？
- **Decision**：No (4.4a non-goal N-12)。Frozen dataclass + Optional field + upcaster chain 為 4.4a baseline；Pydantic migration 留 schema migration phase 統一做（避免分散 multi-phase 各炸一輪）。
