量測日期 2026-11-15..2026-11-20。資料範圍 2022-01-01..2026-11-15（UTC；每輪抓取的終點是該輪開跑時刻）。原始資料不進 repo，留在 VM 上的一次性目錄（位置記在本機個人脈絡檔；步驟 2 完成回補後刪除）。

## 怎麼量的

- 腳本：`spike/fetch_tape.py`（只用標準函式庫、唯讀，不碰 DB）。
- 抓取：`python3 -I fetch_tape.py <OUT> --start 2022-01-01 --pace <秒> [--stop-on-429]`，每個 symbol 一份 CSV `id,mts,amount,rate,period`。可中斷續跑：從檔尾最後的 MTS 接著抓，同一 MTS 的 id 去重。
- 統計：`python3 -I fetch_tape.py <OUT> --summarize > summary.json`，一次串流讀完，記憶體不隨列數成長；VM 上 `nice -n 19` 跑 976 秒。
- 地點：fUST 2022-01..2026-05 在筆電抓，之後搬到 VM，從筆電的檔尾續抓（搬移時兩邊位元組數相同，1704151259），fUSD 全程在 VM。Will 2026-11-15 指示改用 VM、筆電不抓。

## 全域 id 序號假設

抽每月 1 號共 59 天比對：兩個 symbol 共用的 id 為 0，同一天按 id 排序後兩者交錯的次數最少 1,138（`global_id_check`）。**結論：已確認**，trade id 是跨 symbol 共用的序號，同 symbol 相鄰 id 跳號不代表漏資料。

另外，同一個 symbol 依時間排序時，有 4.6–7.2% 的 id 比前一筆小，所以 **id 不能當續抓游標**；續抓要用 MTS，並對同一 MTS 去重（腳本就是這樣做，重複為 0）。

## 頻率限制

公開 `trades/hist`，每次請求最多 10,000 筆：

| 每次請求間隔 | 請求數 | 被拒（HTTP 429） | 出處 |
|---|---|---|---|
| 2.2 秒 | 1,400 | 380 | 筆電第一輪的 `fetch.log`（檔案已刪，數字於 session 中讀出） |
| 15 秒 | 1,950 | 5 | 筆電第二輪的 `fetch.log`（同上） |
| 20 秒 | 10,590 | 0 | VM 上 `fetch_runs.jsonl`：fUST 續抓 251＋fUSD 10,300＋一週增量 39 |

Bitfinex 文件說超過限制時「該 IP 被封鎖 60 秒，期間不能發出任何請求」，沒說公開與私有 API 是否分開計算（[requirements-and-limitations](https://docs.bitfinex.com/docs/requirements-and-limitations)，2026-11-19 讀）。VM 跟 live bot 共用出口 IP，所以在 VM 上一律用 20 秒間隔加 `--stop-on-429`。

## 耗時

- **完整回補**（20 秒間隔）：fUSD 218,350 秒（60.7 小時，10,300 次請求）。fUST 沒有單一一輪的完整耗時，按列數推估約 4,000 次請求、23 小時（推論）。兩個合計約 3.5 天。
- **一週增量**（2026-11-12 起，20 秒間隔，VM）：fUST 215 秒（11 次請求，101,560 列）＋fUSD 579 秒（28 次請求，271,730 列）＝**794 秒**。

## DB 大小

本機拋棄式 PG18，照步驟 2 預設的表形狀放 100 萬列合成資料（`symbol text, trade_id bigint, mts bigint, amount numeric, rate numeric, period smallint`，主鍵 (symbol, trade_id)，索引 (symbol, period, mts)），`VACUUM ANALYZE` 後量 `pg_total_relation_size`：資料表 73.9 MB＋索引 63.2 MB＝**每列約 137 bytes**（實測）。

全部 142,516,187 列 × 137 B ≈ **19.5 GB**（推論：用合成列推算；真實的 `numeric` 位數不同時會有出入）。現在的正式 DB 是 3.1 GB（2026-11-15 量），VM 根磁碟剩 144 GB（2026-11-19 `df -h /`）。

## 停止條件與對後續步驟的影響

- **步驟 1 的停止條件**（任一 symbol 超過 7 天沒有任何成交）：**沒有觸發**。全天期最長空窗：fUSD 6.95 小時、fUST 4.72 小時。
- **步驟 2 的停止條件**（估計大小超過 VM 剩餘磁碟 10%）：19.5 GB／144 GB ≈ 13.5%，**觸發**，交 D1 重評。除了磁碟，每次部署前的備份與 restore test、R2 offsite 備份的大小與時間也會隨 DB 變大（推論，D1 一併評估）。
- **D2（p30 排隊量）**：fUST 的 p30 很稀疏，有 72 天整天沒有 p30 成交，最長 7.9 天沒有 p30 成交（2022 年），p10 每天只有 3 筆。fUSD 的 p30 每天中位數 600 筆、p10 54 筆。fUST p30 在早年的 WFO 窗口很可能需要 D2 的 C 案（參數化平滑）或改成以週為單位彙總。
- **步驟 2 的每週增量 timeout**：794 秒 × 3 ≈ 2,400 秒。現有合計 5,100 秒＋2,400 秒＋300 秒餘裕，`TimeoutStartSec` 至少要調到 7,800 秒。
- **步驟 2 的回補**：VM 上用 20 秒間隔約需 3.5 天，必須可以中斷續跑；續抓游標用 MTS，不用 id。
