# 步驟 1b Spike：replay 的前置事實

量測日期 2026-11-20。成交紀錄是步驟 1 留在 VM 上的 CSV（2022-01-01..2026-11-15）；自己的成交與掛單期限是當天從正式 DB 唯讀匯出（Will 2026-11-20 核准）。原始資料與匯出結果都留在 VM 的一次性目錄（位置記在本機個人脈絡檔），不進 repo。

## 怎麼量的

- 自己的成交：`bfx_research` 角色，`BEGIN READ ONLY` 內 `\copy (SELECT trade_id, symbol, mts_create, offer_id, amount, rate, period, maker FROM funding_trades ORDER BY mts_create)`，64 列。
- 掛單期限：`bfx_research` 沒有 `ledger_observation_offer_history` 的 SELECT（`has_table_privilege` = f），`bfx_operator` 沒有 `funding_trades` 的 SELECT，所以拆成兩支查詢；這支用 `bfx_operator`，`BEGIN READ ONLY` 內 `SELECT venue_offer_id, array_agg(DISTINCT period_days) … WHERE venue_offer_id IN (<上一支的 offer_id>) GROUP BY 1`，19 個 offer 有紀錄。權限沒有更動。
- 比對：`python3 spike/period_join.py <匯出目錄> <成交紀錄目錄>`，用 trade_id 串流比對 CSV，VM 上 22 秒。
- 深度與 replay 成本：`python spike/replay_cost.py /tape/<sym>.csv --cache <dir>`，在 VM 上用 backend image 起一次性容器跑（`--network none --cpus 1 --memory 12g`，autoheal 關閉，成交紀錄唯讀掛載）。

## 1. PERIOD 記的是 bid 還是 offer 的期限：自己的成交分不出來

| 判定 | 筆數 |
|---|---|
| 公開 PERIOD = 我方掛的期限 | 21 |
| 公開 PERIOD < 我方掛的期限 | 0 |
| 找不到當初掛的期限 | 43（67%） |

- 找不到期限的 43 筆都在 2026-05-26..2026-09 之間，之後的 21 筆都找得到。原因沒查，推測是掛單歷史表比這些成交晚開始記錄。這就觸發了停止條件 (0)。
- 根本限制：64 筆全是 2 天期（`funding_trades.period` 與公開 PERIOD 都是 2）。2 天是 Bitfinex 最短的期限，依撮合規則（offer 只跟期限 ≤ 自己的 bid 成交），對手 bid 一定也是 2 天，所以兩種解讀算出同樣的值。就算 64 筆都找得到掛單期限，也分不出是哪一種（推論，依據是支援文章 115003428165 的撮合規則）。
- **處置（Will 2026-11-20 選 A）**：replay 的期限規則採用兩種解讀下都成立的寫法：假想掛單期限 P 只算公開 PERIOD ≤ P 的成交。PERIOD 記 offer 期限時，這條規則剛好正確；記 bid 期限時偏保守，因為會漏掉期限更短的 bid 跟我方長期限 offer 成交的那部分。步驟 3 照這條規則做，報告的已知限制要寫上這點。

## 3. replay 成本：讀檔不是瓶頸

| 項目 | fUSD | fUST |
|---|---|---|
| 列數 | 102,945,338 | 39,570,849 |
| CSV 解析（只做一次，`np.loadtxt`） | 52.8 秒 | 20.0 秒 |
| 依（期限、時間）排序並存成 `.npz` | 26.4 秒 | 6.6 秒 |
| 之後每次載入 `.npz` | 1.94 秒 | 1.7 秒 |
| 陣列大小 | 2.68 GB | 1.03 GB |
| 行程最大 RSS（含 CSV 解析） | 8,671 MB | 3,353 MB |
| 1,000 張假想掛單 replay | 3.32 秒 | 1.68 秒 |

- 量測用的 replay 是成本上限，不是正式邏輯：每張掛單都掃完 7 天窗口內所有相容期限的成交（不會在成交後提早停），利率門檻取窗口中位數。所以 `replay_filled` 恆為 1,000，沒有意義。
- 外推（推論）：決策是每小時一次（`period_structure.py` 的 hourly grid），4.8 年約 42,000 張掛單。所以每個策略設定跑一次的耗時，fUSD 約 140 秒、fUST 約 71 秒，兩個 symbol 合計約 210 秒。每週 1,800 秒的預算約可跑 8 個策略設定；載入 `.npz` 每次 2 秒，占比可以忽略。
- 停止條件 (4)：設定數在 8 個以內就不觸發。WFO 掃描的格子數到步驟 6（決策空間搜尋）才會決定，那時要拿這裡的每設定 210 秒重算。Parquet 延後項的觸發條件是「讀檔是主要耗時」，**這裡量到的不是**，所以不觸發。
- 記憶體：fUSD 的 RSS 8.7 GB，主要來自 `np.loadtxt`。步驟 2 寫每日檔案時直接存成二進位陣列，就不用整份解析 CSV；陣列若用 float32 存利率與金額，大約能減半（推論，沒量）。

## 4. 完整性：自己的成交全部在公開紀錄裡

64 筆中 64 筆用 trade_id 在公開 CSV 找得到（`period_join.py` 的 `not_in_tape` = 0），公開金額的絕對值與 `funding_trades.amount` 一致。找不到的比例 0%，停止條件 (3) 的門檻是 5%：**未觸發**。順帶記一點：其中 6 筆的公開金額是正號（出借方主動，也就是我方掛單碰上當時已有的 bid），其餘 58 筆是負號。

## 5. FRR 成交能否辨識：無法辨識

- 公開 funding 成交紀錄每筆只有 `ID, MTS, AMOUNT, RATE, PERIOD` 五個欄位（`fetch_tape.py` 存下 API 回傳的全部欄位），沒有標記 FRR 的欄位。
- 用「利率剛好等於當時的 FRR」來判別也不可靠：FRR 每次更新之間會變動，`funding/stats` 的 FRR 欄位單位也跟成交利率不同（例如 fUSD 2026-05-10 的 FRR 是 1.12e-06，同期成交利率約 1e-4；`funding_stat_row.py` 的註解）。對不上單位就不能用等值比對。
- **結論：無法辨識。** 步驟 3 照計畫的「不可辨識」分支處理：不排除 FRR 成交，報告的已知限制寫明。我方只掛固定利率單，FRR 單不會跟我方成交（支援文章 115003428165），所以 replay 會高估可成交量，影響方向是偏樂觀。
