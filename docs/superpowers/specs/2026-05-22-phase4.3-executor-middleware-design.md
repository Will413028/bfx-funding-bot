## 1. Goals & Non-goals

### Goals
1. 把目前 `_LedgerWrappedExecutor` 的三個責任（transient retry / heartbeat / ledger event emit）拆成 composable middleware chain，每個 single-responsibility、各自 testable
2. 引入 `DomainEventBus` 作為 canonical event channel，把 Axiom emit 與 ledger live update 從 inline coupling 升級為 subscriber 模型
3. Ledger 拆 `_reserved`（pending offers）+ `_realized`（matched credits）雙 counter，符合 venue accounting mirror + 解開 P&L (realized only) 與 AllocationCap (reserved+realized) 的計算耦合
4. 新增 `ReservationClaimed` / `ReservationReleased` event types，配合既有 `ORDER_FILL`，形成精確 event taxonomy，4.4 BitfinexLive 接 WS `fcn/foc/fcu` 可直接 publish 對應 event
5. 為 Phase 5+ SaaS multi-venue / multi-tenant 留下乾淨擴展點（新 venue = 寫 inner executor + 重用 middleware；per-tenant ledger = future ledger constructor 改參數）

### Non-goals（本 phase 不做）
- BitfinexLiveExecutor 實作（Phase 4.4）
- WS `fcn/fcu/foc` handler 接 bus（Phase 4.4）
- fill_tracker 從 coarse `filled_or_cancelled` 拆 filled vs cancelled（Phase 4.4 WS / hybrid 決定）
- L2 guards (DrawdownGuard / DivergenceRateGuard) 接 `realized_exposure()`（Phase 4.4）
- Outbox + DLQ pattern（Phase 5+ SaaS-prod，bus.publish call site 預留 hook）
- Per-credit-id ledger（Phase 4.4 / 5+，當 WS `fcn` payload 定義 Credit 結構時 evolve）
- Per-tenant ledger / bus / event partitioning（Phase 5+ SaaS）
- `OrderRealizedReturn` event（Phase 5+，credit close / principal return）

## 2. Background & Industry Spectrum

### 2.1 為什麼需要分 submitted vs filled

目前 (Phase 4.2 ship) `_LedgerWrappedExecutor.submit` 對 `result.status in {"submitted","filled"}` 都當成 fill：

```python
if result.status in ("submitted", "filled"):
    self._ledger.on_order_fill(OrderFillPayload(
        cid=result.cid,
        offer_id=result.venue_offer_id or "",
        ...
        is_simulated=True,
    ))
```

4.2 EchoPaperExecutor 永遠 return `"filled"`，paper-safe。4.4 BitfinexLiveExecutor 上線後：
- `POST /v2/auth/w/funding/offer` 立即 return `status="submitted"`（offer placed，尚未 match）
- 真正 fill 是 async — 透過 WS `fcn` (FundingCreditNew) 或 REST polling diff
- 兩者經濟意義不同：
  - **Submitted**: 資金被 Bitfinex wallet reserve（user 在 UI 看到 BALANCE_AVAILABLE 減少）；offer 可能掛幾分到幾天才 match，也可能 cancel/expire
  - **Filled**: offer 對應到 FundingCredit，真實 exposure 開始 accrue APR
- 若 4.4 把 submitted 當 fill 計入 ledger：
  - Offer cancel/expire 時 ledger 不會自動回沖 → ghost exposure
  - P&L / drawdown 計算把 reserved 也納入 → 數字錯
  - AllocationCap 用單 counter 算「為什麼 block」無法 audit 出 reserved vs realized 各佔多少

### 2.2 業界 spectrum — Pre-trade exposure accounting

| 模式 | 典型場景 | 適合 funding bot? |
|---|---|---|
| Single signed net position | Spot trading, market making | No — funding 單方向放貸 |
| Bucket (pending/filled × long/short) | Equity broker, multi-direction | Overkill — 單方向無 buy/sell |
| **Account balance + reserved**（採納） | **Exchange wallet 標準 (Bitfinex 自己就是)** | **Yes** — venue accounting mirror |
| Open-orders-book + position-book CQRS | Event-sourced 高 audit | 採納 (event 已是 Axiom event-sourced) |
| Per-instrument exposure dict | Multi-asset | Phase 5+ extension path |
| HFT only-filled w/ overshoot cap | sub-ms fill latency 場景 | No — funding match 可能掛分鐘到天 |

採納理由：mirror Bitfinex wallet accounting（user 心智模型對齊）+ 與 Axiom event-sourced 既有架構相容 + P&L vs cap 計算解耦 + audit trail 乾淨。

### 2.3 業界 spectrum — Executor wrapping / Event emission

| 模式 | 描述 | 適合? |
|---|---|---|
| Naive single-class | Executor 包山包海 | Anti-pattern |
| Hexagonal / DDD | domain 定 port、adapter 實作、events 由 domain 發 | 是方向但需具體形式 |
| OMS standard (FIX-derived) | OrderRouter + OrderEventBus + PositionManager / RiskEngine 分層 | Yes — 對應 N venue 自然 |
| CQRS / Event-sourced | Commands 流出、Events 流入 event store，read model project | Yes — Axiom 已是 event store |
| **Middleware/Decorator chain（採納）** | **inner pure I/O + cross-cutting concerns 各自 decorator + 經過 event bus fanout** | **Yes — onion model standard** |
| Inline pubsub library (e.g. blinker) | 同上但用第三方 | 自寫 30 行更輕量 |

採納 onion middleware chain + DomainEventBus，等同「OMS standard 在單 process 內的最小實作」。Phase 5+ 拆 process 時 bus 可直接換成 Redis Streams / NATS。

## 3. Architecture Overview

### 3.1 Component map

```
┌──────────────────────────────────────────────────────────────────────┐
│                          daemon.py                                    │
│                                                                       │
│  bus = DomainEventBus()                                              │
│  ledger = await PaperPositionLedger.replay_from_axiom(...)           │
│  bus.subscribe(ReservationClaimed,  ledger.on_reservation_claimed)   │
│  bus.subscribe(OrderFilled,         ledger.on_order_filled)          │
│  bus.subscribe(ReservationReleased, ledger.on_reservation_released)  │
│  bus.subscribe(ReservationClaimed,  axiom_sink.on_event)             │
│  bus.subscribe(OrderFilled,         axiom_sink.on_event)             │
│  bus.subscribe(ReservationReleased, axiom_sink.on_event)             │
│                                                                       │
│  inner = EchoPaperExecutor(...) | BitfinexLiveExecutor(...)          │
│  executor = HeartbeatMiddleware(                                     │
│               ReservationEmittingMiddleware(                          │
│                 TransientRetryMiddleware(inner),                      │
│                 bus=bus),                                             │
│               probe=probe)                                            │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 Middleware composition order (onion)

```
decision → HeartbeatMW         (outermost: outcome-independent observability)
         → ReservationEmittingMW (middle: emit events post-retry final result)
         → TransientRetryMW      (innermost: retry venue call only)
         → inner executor        (pure venue I/O)
```

**理由**：
- TransientRetryMW innermost — 只 retry inner.submit；event emit 不 retry（避免重複 publish）
- ReservationEmittingMW middle — emit post-retry final result（不對中途失敗 publish）
- HeartbeatMW outermost — try/finally 確保 heartbeat 不論 inner 結果都 record（保留既有 I1 invariant）

對照 Express / Koa / ASP.NET Core middleware：observability outermost、business decoration 中間、retry 最內層接 backend。FIX-derived OMS 同形。

### 3.3 Event taxonomy

| Event | 觸發 | Ledger effect | Emit by |
|---|---|---|---|
| `ReservationClaimed` | submit returns status ∈ {submitted, filled} | `_reserved += size` | ReservationEmittingMW |
| `OrderFilled` | offer → credit transition | `_reserved -= size; _realized += size` | Paper: ReservationEmittingMW (status=filled 同 call). Live: BitfinexLive WS `fcn` handler (Phase 4.4) |
| `ReservationReleased` | offer cancel / expire without fill | `_reserved -= size` (floor at 0) | Live: BitfinexLive WS `foc` handler 或 fill_tracker disambiguation (Phase 4.4) |
| `OrderRealizedReturn`（5+） | credit close, principal return | `_realized -= size` | Phase 5+ |

Axiom EventType enum 對應新增：`RESERVATION_CLAIMED`, `RESERVATION_RELEASED`。既有 `ORDER_FILL` 不變。

### 3.4 Ledger 雙 counter

```python
class PaperPositionLedger:
    _reserved: Decimal   # sum of open reservations
    _realized: Decimal   # sum of matched (filled) exposure
    
    def current_exposure(self) -> Decimal:
        return self._reserved + self._realized
    
    def realized_exposure(self) -> Decimal:   # Phase 4.4 L2 guards 預埋
        return self._realized
```

`AllocationCapGuard` 介面不變 — 仍呼叫 `current_exposure()`，內部從 `_exposure` 變 `_reserved + _realized`。

## 5. Data Flow

### 5.1 Paper synchronous path (4.3 ship 後立即作用)

```
T0   signal_engine produces DecisionPayload
T0+δ executor.submit(decision, ctx)
       │
       ▼ HeartbeatMW.submit  ── try
       │   ▼ ReservationEmittingMW.submit
       │   │   ▼ TransientRetryMW.submit
       │   │   │   ▼ EchoPaperExecutor.submit
       │   │   │      └─ return SubmittedOrder(status="filled",
       │   │   │                              cid, venue_offer_id="paper_<uuid12>")
       │   │   └─ result.status == "filled" → 
       │   │      1) await bus.publish(ReservationClaimed(...))
       │   │         ├─ ledger.on_reservation_claimed → _reserved += size
       │   │         └─ axiom_sink.on_event → axiom.emit({event_type: RESERVATION_CLAIMED})
       │   │      2) await bus.publish(OrderFilled(credit_id=None, ...))
       │   │         ├─ ledger.on_order_filled → _reserved -= size; _realized += size
       │   │         └─ axiom_sink.on_event → axiom.emit({event_type: ORDER_FILL})
       │   └─ return result
       └─ finally:
           probe.record_heartbeat("executor")
   return result to signal_engine
```

淨效果：paper 一次 submit 兩個 event back-to-back，ledger 經歷 `reserved += / reserved -= + realized +=`（最終 `realized += size`），對 AllocationCap (`reserved+realized`) 計算與 4.2 行為等價。

### 5.2 Live async path (Phase 4.4 BitfinexLive 上線後預期形態)

```
T0    executor.submit (4.3 chain) → BitfinexLive.submit (POST /funding/offer)
        └─ return SubmittedOrder(status="submitted", cid, venue_offer_id=str(int))
      ReservationEmittingMW: bus.publish(ReservationClaimed) → ledger reserved+=, axiom emit
      HeartbeatMW: record_heartbeat("executor")
      return result

T+30s (async) WS `fcn` arrives → BitfinexLive WS handler
      bus.publish(OrderFilled(cid_from_correlation_map, venue_offer_id, credit_id, ...))
        ├─ ledger.on_order_filled → reserved -=, realized +=
        └─ axiom_sink → axiom.emit ORDER_FILL

或 WS `foc` (offer cancel) → BitfinexLive WS handler
      bus.publish(ReservationReleased(cid, venue_offer_id, reason="venue_cancel"))
        ├─ ledger.on_reservation_released → reserved -= (floor at 0)
        └─ axiom_sink → axiom.emit RESERVATION_RELEASED

或 fill_tracker (REST reconcile backup) tick 偵測 offer disappear
      bus.publish(ReservationReleased(cid, venue_offer_id, reason="missing_from_venue"))
```

### 5.3 Replay path (daemon startup)

```python
PaperPositionLedger.replay_from_axiom:
    events = await axiom_query.query_order_events(account_id, since)
    events = sorted(events, key=lambda e: e["_time"])   # defensive sort
    ledger = cls(account_id)
    for ev in events:
        match ev["event_type"]:
            case "RESERVATION_CLAIMED": ledger._apply_reservation_claimed(payload)
            case "ORDER_FILL":          ledger._apply_order_fill(payload)
            case "RESERVATION_RELEASED": ledger._apply_reservation_released(payload)  # floor + count
            case _:                      log.warning("ledger_replay_skip_unknown ...")
    return ledger
```

- `AxiomQueryProtocol.query_order_events` docstring: 「should return chronological order (`_time` ASC)，consumer additionally defensive-sorts to tolerate implementer regression」
- `_apply_reservation_released`：
  ```python
  delta = min(self._reserved, Decimal(str(payload.size_usdt)))
  self._reserved -= delta
  if delta < Decimal(str(payload.size_usdt)):
      self._replay_floor_hit_count += 1
      log.warning("reservation_release_without_claim ...")
  ```
- `build_daemon` 在 replay 完成後：
  ```python
  if ledger.replay_floor_hit_count > 0:
      probe.update(HealthTarget.LEDGER, HealthStatus.DEGRADED,
                   error_message=f"{ledger.replay_floor_hit_count} floor hits during replay")
      await axiom.emit({"event_type": EventType.HEALTH_CHECK.value,
                        "payload": {"check_target": "ledger",
                                    "status": "degraded",
                                    "replay_floor_hit_count": ledger.replay_floor_hit_count}})
  ```

## 6. Error Handling

### 6.1 分層責任表

| Layer | 錯誤類型 | 處理 |
|---|---|---|
| inner executor | 5xx / network / timeout | raise `TransientError` |
| | 4xx auth | raise `AuthError` / `FatalError` |
| | malformed response | raise (fatal — daemon crash + Koyeb restart) |
| TransientRetryMW | TransientError | retry 1/2/4s（既有 `transient_retry` decorator） |
| | Fatal / Auth | first-attempt propagate |
| | exhausts retries | last exception propagate |
| ReservationEmittingMW | inner raise | propagate; 不 emit 任何 event |
| | bus.publish raise | swallow + log critical（I4-EM；venue submit 已成，downstream telemetry 失敗不回滾） |
| HeartbeatMW | inner raise | try/finally 確保 `record_heartbeat("executor")` 仍 fire (I1) |
| | record_heartbeat raise | swallow（heartbeat 失敗不殺 submit） |
| DomainEventBus.publish | handler raise | `gather(return_exceptions=True)`，個別 handler 失敗 log，不影響其他 handler (I6) |
| ledger handler | raise | bus log + skip。下次 restart replay 修正（Axiom SoT） |
| axiom_sink handler | raise | bus log + skip。Axiom client 內部 buffer+retry 是 transient reliability mitigation；本層失敗代表 client 最終放棄 |

### 6.2 Invariants（鎖進 spec + test）

| ID | Invariant |
|---|---|
| I1 (existing) | `record_heartbeat("executor")` 在 submit 後一定 fire，不論 inner 結果 |
| I2 (existing) | Transient 錯誤 retry 1/2/4s 才 propagate；Fatal/Auth 第一次就 propagate |
| I3-EM (new) | `ReservationEmittingMW.submit` 對 `result.status == "failed"` 不 emit 任何 event |
| I4-EM (new) | `bus.publish` 失敗不該讓 submit 失敗（Axiom emit 失敗不回滾 venue 動作） |
| I5-Ledger (new) | `on_reservation_released` floor-at-0；不對稱觸發 log warning 並計 `replay_floor_hit_count` |
| I6-Bus (new) | handler 例外不影響同 event 的其他 handler |
| I7-Replay (new) | replay 後 `replay_floor_hit_count > 0` → `probe.update(LEDGER, DEGRADED)` + emit health event |
| I8-Order (new) | 同一 submit 內 `ReservationClaimed` 必先於 `OrderFilled` publish（paper sync 路徑）|

### 6.3 Forward-compat hook（Phase 5+ outbox/DLQ）

`bus.py` 與 `ReservationEmittingMiddleware._publish_event` 處註明：

```python
# FORWARD-COMPAT (Phase 5+): outbox pattern upgrade point.
# Future: persist event to Postgres outbox table before publish; publisher
# service polls outbox and forwards to Axiom + ledger handlers with
# idempotency tokens. Failed publishes go to DLQ; reconciler retries.
# Current scope: in-process gather() + log on swallow; Axiom client's
# internal buffer+retry covers transient failures.
```
