# Phase 4.1 — Paper / Shadow Infrastructure Design

## Context

Phase 4 Roadmap（2026-05-18 完成，`2026-05-18-phase4-roadmap-design.md`）把 paper/shadow/canary 切成 4 個 sub-spec：4.1（paper/shadow infra）、4.2（real-money safety + execution）、4.3（stability calibration）、4.4（first canary）。本 spec 是 4.1。

4.1 範圍（roadmap 第 61 行）：

- Live market feed 接線（Bitfinex WebSocket candles channel）
- Signal logging（per candle 計算 + 記錄）
- 無下單 dry path（decision 寫 log 不下單）
- Divergence reporter（live 與 backtest 對齊性檢查）

**Schema 已 lock**：envelope + `signal` / `decision` / `health_check` event payload 訂在 roadmap line 92-227，本 spec 引用不重訂。`order_submit` / `order_fill` / `safety_trigger` 是 4.2 範圍，4.1 不 emit。

**Python backend 現況**：`backend_py/src/bfx_funding_bot/external/bitfinex/rest.py` 已有 REST + aiolimiter；`modules/backtest/strategies/` 有 RatePercentile / MeanReversion 兩個 candle-driven strategy；`modules/candles/` 有 `funding_candles` DB table + REST backfill；**沒有 marketfeed / 沒有 WS / 沒有 worker**。4.1 等於從 0 蓋 live-feed → signal → decision 路徑。

**G1 pass criteria（roadmap 第 270 行）**：

- ≥ 1hr 連續 live signal logging without crash
- All signals 寫進 DB（重解為 Axiom ingested；事件持久化目的地由本 spec Q9 決議）
- Signal value 落在 Phase 3b EDA 觀察區間
- Axiom dashboard 看得到 metric stream（4.4 dashboard sub-spec 才解凍）

## Decision Summary

| Decision | Lock |
|---|---|
| Q2 Signal compute cadence | Candle-close-driven（跟 Phase 3b 對齊）|
| Q3 Divergence reporter scope | Code-replay only（forecast-vs-actual 屬 4.3）|
| Q4 Divergence reporter 實作 | In-process dual-compute |
| Q5 Phase 機制 | `BFX_PHASE` env var；無 auto-exit；G1 smoke 外掛 script |
| Q6 WS channels | Candles only |
| Q7 Cell scope | Config-driven（default = Phase 3b 11 qualified pairs）|
| Q8 Strategy state warmup | DB read N candle + REST gap-fill + WS attach |
| Q9 Event persistence | Axiom primary；4.1 不建 Postgres event tables |
| Q10 WS resilience | 自寫 `websockets` client + exp backoff + REST gap-fill |
| Q11 `observe()` trigger | Time-driven scheduler `mts + timeframe + 5s` |
| Q12 `decision.offer_amount_usdt` 來源 | Cell config placeholder（default $150）|
| Architecture | Layered services（對應 Go-era `backend_architecture.md`）|

## Design Decisions

### Q2 — Signal compute cadence

Strategy candle-close-driven，**不**做 tick-driven 或 hybrid。

**Rationale**：

1. Phase 3b WFO 結果是 candle-close 值；G2 signal-level match rate 需 apples-to-apples 比對
2. Phase 4 目標是「驗證 backtest 假設成立」，introducing 新 cadence 等於同時換兩變數
3. 4.4 first canary 是真錢，cadence 不確定性留 Phase 5

### Q3 — Divergence reporter scope

4.1 做 **code-replay divergence**：偵測「live pipeline 算出的 signal vs 直接用 backtest module 跑出來的 signal」是否一致 — 抓 code correctness / 資料 path 偏移。

Forecast-vs-actual（live signal vs Phase 3b 預期 trajectory）屬 **4.3** — G2 metric M1 就是 forecast-vs-actual 的形式化版。

**Rationale**：

1. Scope hygiene — 4.1 是 infra 正確性；4.3 是 strategy/market 有效性
2. Phase 3b FRR 兩種接法（`market_rate_source="frr"` vs `"candle_close"`）已踩過 silent divergence；code-replay 是直接保險
3. G1 criterion #3（signal 值落在 EDA 區間）已是粗糙版 code-replay；4.1 正式版做厚自動 alert

### Q4 — Divergence reporter 實作

**In-process dual-compute**：每 candle close，pipeline 同時跑 (1) live Strategy instance、(2) backtest replay 從 history 重新跑到當下 → diff 兩邊 `signal_score` / `signal_direction`。

| 派別 | 為何不選 |
|---|---|
| Async batch reconciler | divergence 發現延遲長；不利 G1 即時發現 |
| Single-pipeline + invariant assertions only | 抓不到 silent state divergence（如 warmup 缺一筆 candle）|

**Rationale**：

1. Backtest replay 對 11 cell × ~千筆 candle 是毫秒級
2. G1 1hr smoke 內可直接 catch divergence → emit `level=warn` event
3. Phase 3b 已有 silent divergence 踩坑前例

### Q5 — Phase 機制

`BFX_PHASE` env var 驅動，single daemon code path，**無 auto-exit**。G1 smoke validation 用獨立 script `scripts/g1_smoke_check.py`（外掛 deployment gate）。

| 派別 | 為何不選 |
|---|---|
| CLI subcommand（Freqtrade style）| 多一層 CLI verb 抽象，無收益；2 個 mode 不值得 |
| 操作者宣告（無 env var）| phase envelope 欄位必填 → 必須有 source；env var 比 hardcode 有 audit trail |
| 我原版 mode flag + auto-exit | Hobbyist over-engineering；業界 Hummingbot / Freqtrade 都是無 auto-exit |

**Rationale**：

1. Schema envelope `phase` 必填 → env var 是最自然 source
2. Koyeb 部署模型對齊（Docker image + env var 切 phase）
3. 對應 Hummingbot / Freqtrade 等業界 closest analog
4. 為 4.2 留乾淨升級路徑：`phase=canary` 之後升級成 DI executor swap 觸發條件

### Q6 — WS channels

只訂閱 **candles**（每 cell 一個 channel：`trade:<timeframe>:<symbol>:<period_agg>`）。不訂 ticker / funding book。

**Rationale**：

1. 策略只吃 candle close（RP deque、MR EMA / ratio_sigma）
2. Schema lock 沒 ticker / book event_type，多訂無處可記
3. Bitfinex `hb` heartbeat ~15s 一次 — `health_check.last_msg_age_ms` 不會誤觸
4. Channel quota：6 candles channels（cells 用 period_agg 區分；fUSD/fUST × p2/p30/a30）遠低於 Bitfinex 30 channel/conn 限制
5. 業界 Lean DataSubscription / Hummingbot per-strategy needs 的「策略宣告什麼就訂什麼」共識

### Q7 — Cell scope

**Config-driven list**（`configs/cells.yaml` + `BFX_CELLS` env override），default = Phase 3b 11 qualified pairs（RP 6 cells + MR 5 cells，缺 MR×fUST×p30）。

**Rationale**：

1. Pre-canary multi-cell shadow 是 quant 教科書 best practice（Two Sigma / Marcos López de Prado）— 避免 backtest 過擬合 single-pick
2. 4.3 G2 calibration 需要 multi-cell sample（11 pair vs 1 pair 的 statistical power 差距大）
3. 6 candles channels + 24 series cardinality 都在 schema lock 上限內（≤ 50）
4. Config 化保留 ops 動態調整彈性（incident 關 cell 不必 redeploy）
5. 避免 4.4 pre-commit bias：shadow 數據可能改變 4.4 候選排序

### Q8 — Strategy state warmup

**DB warmup + REST gap-fill + WS attach**：

1. 讀 `funding_candles` 最後 N candle 餵 `strategy.observe()`
2. 比對 DB 最新 mts vs now，> 1 candle interval 觸發 `gap_fill.fetch_rest()`
3. Attach 到 WS 從 "now" 接

| 派別 | 為何不選 |
|---|---|
| WS-only cold start | RP lookback 168 + 1h timeframe → 168hr 才 warmup，G1 1hr smoke 不可行 |
| REST warmup + state checkpoint | 4.1 是 build phase；restart 重 warmup 秒級成本；序列化引版本兼容問題 |
| 純 REST polling | 放棄 push-based health_check |

**Rationale**：

1. B 不可行（warmup 時間 vs G1 smoke 期限矛盾）
2. C 過度工程
3. Gap reconciliation 必須 — backfill 是 batch 流程，與 daemon 啟動瞬間有天然缺口
4. Dual-compute 對齊：live 跟 backtest replay 都 consume 同一 DB；A 的 WS-寫-DB 流程保證 source-of-truth 一致

### Q9 — Event persistence

**Axiom primary**：`signal` / `decision` / `health_check` 直接 emit Axiom HTTP ingest API。4.1 不建 Postgres event tables。`funding_candles` Postgres table 維持既有（warmup + dual-compute 來源）。

| 派別 | 為何不選 |
|---|---|
| Postgres primary + Axiom 同步 | events 為 diagnostic，不適合占用 transactional DB；canary 期累積近百萬列要 partition |
| Dual-write 兩邊 | eventual consistency + 雙實作 emit |
| In-process buffer batch flush | 4.1 量小（~25 events/hr）過度設計 |

**Rationale**：

1. Trading firm 教科書分工：log platform 給 diagnostic events，relational DB 給 transactional invariants
2. Roadmap 第 80 行已提 hosting 在 Axiom；retention（第 206 行）也訂在 Axiom
3. Schema envelope `correlation_id` / nested `payload` 是 log-event 結構，硬塞 Postgres 退化成「DB 假裝 log platform」
4. Divergence reporter in-process 不靠 DB，不需 join 查 divergence
5. 4.2 加 `order_submit` / `order_fill` 是 transactional → 該時點建 Postgres orders table（不違反此分層）

### Q10 — WS resilience

**自寫 `websockets` lib client + exp backoff + reconnect 時 REST gap-fill**：

- Backoff schedule：1s → 2s → ... → 60s cap
- Connection 存活 ≥ 5min reset backoff
- 5 次連續 fail → emit `health_check level=error status=down`，繼續 retry，**不退 daemon**
- Reconnect 成功立即 REST gap-fill `last_known_mts → now`，再 resubscribe

| 派別 | 為何不選 |
|---|---|
| Naive immediate reconnect | Hammer Bitfinex；違反 docs 建議 |
| Circuit breaker（N 次失敗後停 + alert）| 4-6 week canary 不能凌晨要求介入 |
| 用官方 `bfxapi` Python SDK | lib quality 一般；`health_check` schema 對應要 wrap 反向出資料，介面易碎；funding period_agg 變體支援未必跟得上 |

**Rationale**：

1. Schema lock 倒推 — `reconnect_count_last_hour` / `last_msg_age_ms` 必須是我們的 client 主動 emit
2. Bitfinex WS 不複雜，`websockets` lib + 100-150 行就夠
3. Gap-fill 邏輯跟 warmup 復用 — 同一 helper 兩處用
4. 4-6 week canary 期不可能要求 crash daemon 後操作者重啟

### Q11 — `observe()` trigger

**Time-driven scheduler**：`mts + timeframe + 5s` 排程 fire；WS 純做 DB writer 角色。

| 派別 | 為何不選 |
|---|---|
| WS-event-driven（偵測下個 mts WS 事件）| Funding low-activity 時段無新成交 → 下個 mts 不會來 → observe 卡住 |
| Hybrid（WS primary + time fallback）| 4.1 過度設計 |
| Streaming on partial candle | 破壞跟 backtest 的對齊 |

**Rationale**：

1. Funding candles 低活躍時段是常態（凌晨 / 週末）— event-driven 卡住
2. Scheduler 對齊 divergence reporter — backtest replay 自然 mirror live timing
3. WS 純粹 DB writer：架構分工乾淨，scheduler 跟 WS 完全 decouple
4. 5s buffer 吸收 WS 抵達 jitter + Bitfinex 端候到的 candle 修正

**Race condition 防護**：scheduler 在 `mts + timeframe + 5s` 讀 DB 時，若該 mts row 仍空 → emit `health_check level=warn status=degraded error_message=candle_missing_at_scheduled_observe`，該 tick skip。

### Q12 — `decision.offer_amount_usdt` 來源

**Cell config placeholder**（`configs/cells.yaml` 每 entry 有 `reference_amount_usdt`，default $150 = Bitfinex funding minimum）。4.1 spec 明確標註此為 placeholder；4.2 升級為真實 allocation。

| 派別 | 為何不選 |
|---|---|
| Strategy.decide() 加 amount 簽名 | 越界 — strategy 不該知道資金；改動 backtest 也跟著要回填，G2 calibration 跑歷史會混 |
| Skip amount（emit null）| Schema violation |
| Live wallet REST 拉 balance × ratio | 越界 4.2 — 接 wallet 是 4.2 第一步 |

**Rationale**：

1. Schema lock `offer_amount_usdt` post 必填，必須有值
2. Strategy 解耦：rate × period 是 Phase 3b WFO ground truth；allocation 是 4.2 layer
3. Divergence reporter byte-equivalence 不受 amount 影響（比對 `signal_score` / `signal_direction`）
4. G2 metric 不看 amount
5. 4.2 升級乾淨：`decision.offer_amount_usdt` 從「讀 cell config placeholder」改成「讀 cap manager + wallet balance」一個函數

### Architecture — Layered services

Layered services pattern：對應 Go-era `backend_architecture.md` marketfeed / signal / strategy / execution / worker 子 package 分工的 Python 變體。

| 派別 | 為何不選 |
|---|---|
| Reactor pattern + handler registry | Trading 邏輯有清楚 stage（data → state → strategy → execution）；reactor 「any handler 處理 any event」靈活度過剩、audit 困難。LMAX Disruptor 是 HFT exception，funding bot 秒-分鐘 cadence latency 不是 driver |
| Per-cell worker tasks | bfx-funding-bot 目前 single-user；per-user worker 是 Phase 6+ SaaS 化才有意義 |
| Hexagonal / clean architecture（domain / application / infra）| Java/Kotlin enterprise idiom；Python trading 圈不採；既有 repo 沒採 |

**Rationale**：所有主流 Python retail trading systems（Freqtrade、Hummingbot、Jesse、Backtrader、Lean）都用 layered services。對應業界 universal best practice；既有 Go-era architecture 也是 layered。

## Data Flow

四個關鍵 flow：startup warmup（一次性）、steady-state per-candle（每 N 分鐘 per cell）、WS reconnect、health monitor cadence。Shutdown 是 reverse of startup。

### Flow 1 — Startup warmup（一次性）

```
daemon.main()
   │
   ├─→ config.load() ────→ 讀 BFX_PHASE / BFX_CELLS env var + cells.yaml
   │                          產出 List[CellConfig]
   │
   ├─→ warmup.run(cells):
   │      for each cell in cells:
   │         1. last_mts = candles_repo.get_max_mts(cell)
   │         2. now_mts = wall_clock_aligned_to_candle()
   │         3. if (now_mts - last_mts) > timeframe:
   │              gap_fill.fetch_rest(cell, last_mts, now_mts)
   │         4. strategy = strategy_factory(cell.strategy_type, cell.params)
   │         5. history = candles_repo.get_last_n(cell, lookback_hours)
   │         6. for candle in history: strategy.observe(candle)
   │         7. registry.put(cell, strategy)
   │
   ├─→ ws.connect()
   │      subscribe candles channel × N cells
   │
   └─→ asyncio.gather(
          candle_writer.run(),
          scheduler.run(),
          health_monitor.run(),
       )
```

**Invariants**：

- Warmup 完成才 attach WS
- Strategy registry key = `(strategy_type, symbol, period_agg)` — 11 entry
- Strategy state 每 daemon 結束就丟（無 checkpoint，Q8 已排除）

### Flow 2 — Steady-state per-candle

```
scheduler 在 wall-clock = mts + timeframe + 5s 觸發 per cell:
   │
   ├─→ correlation_id = uuid4()
   │
   ├─→ candle = candles_repo.get(cell, mts)
   │      ├─ if None: emit health_check(level=warn, status=degraded,
   │      │            error_message="candle_missing_at_scheduled_observe")  ← END
   │      └─ else: continue
   │
   ├─→ strategy = registry.get(cell)
   │
   ├─→ live_signal = strategy_extract(candle, strategy):
   │      strategy.observe(candle)
   │      lend_decision = strategy.decide(candle)
   │      signal_score = normalize(lend_decision, strategy)
   │      signal_direction = "post" if lend_decision else "skip"
   │      strategy_attributes = per-strategy attrs
   │
   ├─→ axiom.emit(
   │      event_type="signal",
   │      correlation_id, cell, strategy,
   │      payload={signal_score, signal_direction, strategy_attributes}
   │   )
   │
   ├─→ divergence_reporter.check(cell, candle.mts, live_signal):
   │      replay_strategy = strategy_factory(...)
   │      history = candles_repo.get_up_to(cell, candle.mts, inclusive=True)
   │      for c in history: replay_strategy.observe(c)
   │      replay_signal = strategy_extract(history[-1], replay_strategy)
   │      if not signals_equal(live_signal, replay_signal):
   │         # SUPERSEDED 2026-05-21: divergence emit uses event_type=signal_divergence
   │         # (orthogonal to severity), not overloaded level=warn on event_type=signal.
   │         # Was causing C2 emit-completeness query to over-count 2 vs 1 per cell-hour
   │         # whenever divergence fired. See backend_py/src/.../signal_engine.py.
   │         axiom.emit(event_type="signal_divergence", level=warn, ...,
   │            payload={..., divergence_detail: {...}}
   │         )
   │
   ├─→ decision = build_decision(live_signal, cell.reference_amount):
   │      if signal_direction == "post":
   │         decision_outcome = "post"
   │         offer_rate = lend_decision.rate
   │         offer_amount_usdt = cell.reference_amount  ← Q12 placeholder
   │         offer_duration_days = lend_decision.period_days
   │      else:
   │         decision_outcome = "skip"
   │         skip_reason = "below_threshold"
   │
   └─→ axiom.emit(event_type="decision", correlation_id, ..., payload=...)
```

**Invariants**：

- signal + decision 共用同一 `correlation_id`；`decision.signal_correlation_id` = envelope `correlation_id`（schema lock 規定）
- Divergence reporter 重建 strategy from scratch — 確保 replay 是 stateless reproduction
- Replay 用 `candles_repo.get_up_to(cell, mts, inclusive=True)` — 同 DB row 來源保證 byte-equivalence
- 4.1 `skip_reason` 只可能 `below_threshold`（`safety_block` / `max_position_cap` / `insufficient_balance` 是 4.2/4.4）

### Flow 3 — WS disconnect → reconnect

```
ws task 偵測 disconnect / hb timeout (>30s no msg):
   │
   ├─→ reconnect_attempt += 1
   ├─→ emit health_check(level=warn, status=degraded, check_target=bitfinex_ws,
   │      reconnect_count_last_hour, error_message)
   │
   ├─→ backoff_secs = min(2 ** (reconnect_attempt - 1), 60)
   ├─→ await asyncio.sleep(backoff_secs)
   │
   ├─→ try ws.connect() + resubscribe:
   │      ├─ success:
   │      │    for each cell:
   │      │       last_mts = candles_repo.get_max_mts(cell)
   │      │       gap_fill.fetch_rest(cell, last_mts, now)
   │      │    if connection_alive >= 5min:
   │      │       reconnect_attempt = 0
   │      │    emit health_check(level=info, status=healthy)
   │      │
   │      └─ fail:
   │           if reconnect_attempt >= 5:
   │              emit health_check(level=error, status=down,
   │                 error_message="reconnect_failed_5_consecutive")
   │              # 不退出 daemon
   │           loop back to top
```

**Invariants**：

- Daemon **永不主動退出**（除非 SIGTERM）— 失敗只 emit health_check
- Gap-fill 在 reconnect 成功後立即跑；scheduler 下次 fire 時 DB 已補齊
- `reconnect_count_last_hour` 用 rolling window 計算（在 health_monitor 維護）

### Flow 4 — Health monitor cadence

```
health_monitor task：
   │
   ├─→ 訂閱 ws / db / redis 狀態變化 channel（in-process pub-sub）
   │      狀態變化即 emit health_check
   │
   └─→ 每 300s（5min）強制 emit heartbeat：
          for each check_target in [bitfinex_ws, db, redis]:
             current_status = probe(check_target)
             emit health_check(status=current_status, ...)
```

**Invariants**：

- Schema lock 第 171 行訂死：「狀態變化 emit + 每 5min 強制 heartbeat」
- 5min heartbeat 讓 Axiom 端 alert rule 可用「ws 過 5min 無 health_check」判 daemon 自身掛了

### Task topology

```
asyncio event loop:
├── ws_task            ─→ recv WS → 寫 in-memory queue
├── candle_writer_task ─→ queue → funding_candles upsert
├── scheduler_task     ─→ per-cell timer → trigger Flow 2
├── health_monitor_task → Flow 4
└── divergence inline 在 scheduler_task 內呼叫

外掛 g1_smoke_check.py 完全獨立進程
```

單一 asyncio event loop，無 multiprocessing / multithreading。

## Configuration

### Env vars

| Var | Required | Values / Default | 用途 |
|---|---|---|---|
| `BFX_PHASE` | ✓ | `paper` / `shadow` | Envelope `phase` 欄位來源；4.1 daemon 不接 `canary`（fail-fast） |
| `BFX_CELLS` | optional | 空 = 全 11 pairs；逗號分隔 subset | 例：`mean_reversion:fUSD_a30,rate_percentile:fUST_p2` |

## Error Handling & Resilience

### Error taxonomy

| Failure mode | Layer | Severity | Action |
|---|---|---|---|
| Bitfinex WS disconnect / hb timeout | WS client | Recoverable | Flow 3 backoff reconnect；emit `health_check level=warn status=degraded` |
| WS reconnect ≥ 5 consecutive fail | WS client | Degraded persistent | emit `health_check level=error status=down`；繼續 backoff，不退 |
| Candle DB upsert fail | candle_writer | Recoverable | Retry 3 次（100ms / 500ms / 2s）；仍 fail → emit `level=error check_target=db`；continue |
| Postgres connection pool exhausted | candle_writer / scheduler | Recoverable | 觸發 pool reset；emit health_check error；continue |
| Postgres unreachable > 60s 內 ≥10 次 retry | core | Catastrophic | exit 1 → Koyeb restart |
| Axiom emit HTTP fail | axiom client | Recoverable | Retry 3 次 + 失敗事件本地 stdlib log；不阻塞 caller |
| Axiom emit 持續 > 5min fail | axiom client | Degraded persistent | fallback：stdout JSON line（Koyeb log capture）；每 30s 試重連 Axiom；不退 |
| Axiom 401 / 403 | axiom client | Fatal config | exit 1 |
| Candle missing at scheduled observe | scheduler / signal_engine | Recoverable | emit `health_check status=degraded error_message=candle_missing`；該 tick skip |
| Strategy.observe / decide raise exception | signal_engine | Logic bug | catch；emit `health_check level=error error_message="strategy_exception: <exc>"`；該 tick skip；該 cell strategy state 視為 corrupted → 重 warmup |
| Divergence reporter exception | signal_engine | Logic bug | catch；emit warn-level event with stack；不影響 live signal/decision emit |
| Strategy params schema mismatch | config | Fatal config | exit 1 |
| `BFX_PHASE=canary` | config | Fatal config | exit 1 |
| Phase 3b qualified-cell warn | config | Soft warn | log warning；繼續 |

### Retry policies

| Dep | Strategy | Cap | 失敗後動作 |
|---|---|---|---|
| Bitfinex WS | Exp backoff 1s → 60s | Unbounded | 5 次連續 fail 升 `level=error`，繼續 retry |
| Bitfinex REST（gap-fill）| 既有 `rate_limit.py` aiolimiter + Retry-After | 3 次 | Gap-fill 放棄 → emit warn；下次 WS update 補齊 |
| Postgres | Exp backoff 100ms / 500ms / 2s | 3 次 | 累計 > 60s 內 ≥10 次 fail → daemon exit 1 |
| Axiom HTTP | Exp backoff 200ms / 1s / 5s | 3 次 + stdout fallback | 401/403 立即 exit 1；其他走 fallback |

**通則**：retry library 用 `tenacity`（新依賴，Python 標準 retry lib）；所有 retry 有上界；觸發 retry 即 emit `health_check level=warn`。

### Graceful shutdown

```
SIGTERM / SIGINT 收到:
   ├─→ stop accepting new schedule ticks
   ├─→ 等已啟動的 Flow 2 跑完（max 10s timeout）
   ├─→ ws.disconnect()
   ├─→ axiom.flush()
   ├─→ db_pool.close()
   └─→ emit health_check(status=down, error_message="graceful_shutdown")
       exit 0
```

**保證**：

- 已生成 `correlation_id` 的 signal/decision pair 不會半邊漏 emit
- Axiom in-process batch 不丟失
- 10s 上限（避免 Koyeb kill -9）

### Daemon 永不主動退出的 exception list

1. **Config fatal**：env var 缺、yaml syntax 錯、Pydantic validate fail、`BFX_PHASE=canary` → exit 1
2. **Auth fail**：Axiom 401/403 → exit 1
3. **Catastrophic infra**：Postgres unreachable > 60s 內 ≥10 次 fail → exit 1
4. **Signal**（SIGTERM / SIGINT）→ graceful shutdown → exit 0
5. **Uncaught exception in core task**：強制 promote 為 daemon exit 1（避免半死狀態）

其他全部 emit + continue。

### Why no circuit breaker

WS / DB / Axiom 是 critical path，break 了無 fallback；Bitfinex REST 已有 aiolimiter。Circuit breaker 對「需要持續 retry 才能 recover」場景沒收益、拖長 recovery time。4.1 用 plain retry + observability 取代。4.2 加 Bitfinex offer/new API 才有意義。
