# Phase 4.1 — Koyeb Paper/Shadow Deploy Design

**Date**: 2026-05-18
**Status**: Design approved, pending implementation plan
**Related**:
- [Phase 4.1 paper/shadow infra design](./2026-05-18-phase4.1-paper-shadow-infra-design.md)

## Context

Phase 4.1 application infra（marketfeed daemon、cells.yaml、22-task plan）已實作完成且本機測試通過（197 unit + 4 integration + 2 benchmark pass）。但 build/ship 那層（containerization、Koyeb 設定、deploy runbook）原 plan 未涵蓋。本 spec 填補這個 gap，讓 paper 1hr smoke 與 shadow 2-4 週 run 可以實際在 Koyeb 上跑起來。

「Deploy-ready」原宣告 leak 了一層 infra — 本 spec 範圍即是 close 這層。

## Goals

1. Backend_py 能透過 Koyeb 自動 build & deploy（Dockerfile + git push trigger）
2. Container 啟動時自動套 alembic migration → 起 marketfeed daemon → SIGTERM 正確退 0
3. Paper 1hr 跑完自動退（`BFX_RUN_DURATION_HOURS=1`）→ 本機 `g1_smoke_check.py` 拿 G1 PASS
4. Shadow flip 僅需改 2 個 env var + redeploy（無 code change）
5. Runbook 自完備，下次 deploy 不需回想細節

## Non-Goals

- **Real-money execution**（Phase 4.2+ 範圍）
- **Multi-instance / multi-region**（Phase 4.1 single-replica 即可）
- **CI/CD pipeline**（git push → Koyeb auto-deploy 已足夠，不另設 GitHub Actions）
- **Image registry 自管**（用 Koyeb 內建 build；之後要遷 GHCR / ECR 再說）
- **Frontend deploy**（Vercel，已就位，與本 spec 無關）
- **Go backend 廢棄處理**（封存中，本 spec 不動）

## Decisions

| # | 議題 | 決定 | 理由 |
|---|---|---|---|
| D1 | Artifact 範圍 | Dockerfile + runbook 文件 | 平衡 reproducibility 與 surface area；IaC（koyeb.yaml）暫不導入 |
| D2 | Alembic migration | Container start 時自動跑 | Single-replica + solo dev 場景下 fail-fast 即可，比手動更不易漏 |
| D3 | Dockerfile 構造 | Single-stage（option A） | Phase 4.1 image size 非瓶頸；維護成本最低；之後優化再升 multi-stage |
| D4 | Image base | `python:3.13-slim` | uv + 二進制 wheel（numpy/pandas）相容；非 alpine（musl libc 衝突風險） |
| D5 | uv 安裝方式 | `pip install uv==0.5.*` | 顯式版本鎖；不依賴 Astral 官方 base image |
| D6 | cells.yaml | Bake into image | Phase 4.1 不 hot-tune params；tuning 在 Phase 4.3 calibration |
| D7 | Build context | `backend_py/` | Python 程式碼全在這層，避免 Go backend / frontend 進 image |
| D8 | Container user | Non-root（`appuser` UID 1000） | 安全 baseline；無需 root capability |
| D9 | Signal handling | `exec bfx-shadow`（CMD 用 sh 但 exec 替換 process） | Python daemon 才能收到 Koyeb 發的 SIGTERM 走 graceful shutdown |
| D10 | Axiom dataset 名 | `bfx-funding-bot` | 對齊 project name；paper/shadow 共用 dataset，靠 event payload `phase` 欄位區分 |
| D11 | 本機 docker build smoke | 寫完先 `docker build` + `docker run --help` | 省 Koyeb build cycle，<3min 就能抓到 typo / 缺檔 |
| D12 | Rollback 策略 | Revert commit + push（Koyeb auto rebuild） | Single-replica 不需 versioned snapshot；簡單 |
| D13 | cells.yaml path resolution | Dockerfile 設 `ENV BFX_CELLS_YAML=/app/configs/cells.yaml` | Self-review 發現 `daemon.py:374` 呼叫 `build_daemon()` 無參數 → `load_config(None)` 落到 `config.py:127` 的 `parents[4]` broken path（container 內 site-packages 解析錯）。Image-baked env var 是 deploy 層最小侵入修法；治本（修 daemon 預設）列為 Phase 4.2 code-debt |

### Container layer 切分

| Layer | 內容 | Cache 失效條件 |
|---|---|---|
| L1: base image + apt deps + uv | `python:3.13-slim` + `build-essential` + `uv==0.5.*` | base image 或 uv 版本變 |
| L2: dependency resolution | `pyproject.toml` + `uv.lock` → `uv sync --frozen --no-dev` | pyproject / lock 變 |
| L3: application code | `src/` + `alembic/` + `alembic.ini` + `configs/` + `scripts/` | 任一檔變 |
| L4: runtime config | `useradd` + `chown` + `PATH` | L3 變 |

dependency 層在程式碼層之前 → 改 code 不會重 install dependencies，rebuild 約 10-30 秒。

### Dockerfile（具體內容）

```dockerfile
FROM python:3.13-slim AS base

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    UV_LINK_MODE=copy \
    UV_PROJECT_ENVIRONMENT=/app/.venv

RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential \
    && rm -rf /var/lib/apt/lists/* \
    && pip install --no-cache-dir uv==0.5.*

WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

COPY src/ ./src/
COPY alembic/ ./alembic/
COPY alembic.ini ./
COPY configs/ ./configs/
COPY scripts/ ./scripts/

RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

ENV PATH="/app/.venv/bin:$PATH" \
    BFX_CELLS_YAML=/app/configs/cells.yaml

CMD ["sh", "-c", "alembic upgrade head && exec bfx-shadow"]
```

## Risk & Mitigation

| Risk | 機率 | Impact | Mitigation |
|---|---|---|---|
| numpy/pandas wheel 沒 py3.13 prebuilt → build 超慢 | 中 | image build 3-10 分鐘 | 留 `build-essential` 在 image 內；如果真的太慢再考慮 multi-stage |
| `uv sync --frozen` 與 host 鎖檔 ABI mismatch | 低 | container 啟動報 import error | `uv.lock` 已存在 repo 且本機驗證；docker smoke 會抓到 |
| Migration 在 startup 失敗導致 daemon 不起 | 低 | Koyeb restart loop | Fail-fast log → runbook troubleshooting 列出解法 |
| Koyeb worker 預設 SIGTERM grace period 不夠 → daemon 沒 drain 完 | 低 | Axiom event 漏寫 | `exec` chain 確保 SIGTERM 達到 Python；Koyeb default 60s grace 對 marketfeed flush 足夠 |
| Axiom token 誤貼進 chat / git | 高 | token compromise | Runbook 明文「直接填 Koyeb env，不經 chat / repo」 + `feedback_secret_handling_in_chat.md` memory |

### Code-debt (defer to Phase 4.2)

本 spec 用 runbook / Dockerfile workaround 繞過、但治本應在 code-side 修正的項目。Phase 4.2 brainstorm 時納入範圍清單：

- **`daemon.py:374` 預設 cells.yaml lookup 損壞** — `build_daemon()` 無參數呼叫 → `load_config(None)` 落到 `config.py:127` 的 `Path(__file__).parents[4]` 在 site-packages 場景解到錯誤路徑。本 spec 用 D13 image-baked env var 繞過；治本應改 daemon 提供 cwd-based 或 importlib.resources 的 sane default。
- **`DATABASE_URL` 與 asyncpg 不相容 — 4 處 manual transform** — Neon dashboard 給 libpq-style `postgresql://user:pass@ep-xxx-pooler.<region>.aws.neon.tech/db?sslmode=require&channel_binding=require`，但 SQLAlchemy + asyncpg 需要：
  1. Scheme `postgresql+asyncpg://`（否則走 psycopg2，image 沒裝）
  2. `?ssl=require` 取代 `?sslmode=require`（asyncpg 不認識 `sslmode` keyword，會炸 `TypeError: connect() got an unexpected keyword argument 'sslmode'`）
  3. 移除 `&channel_binding=require`（asyncpg 不支援 channel binding 協商）
  4. 移除 `-pooler` 後綴用 direct endpoint（migrations 必走 direct；asyncpg prepared statements 與 PgBouncer transaction-mode 衝突）

  本 spec 用 runbook 要求 user 手動轉。**治本**：在 `core/settings.py` 的 `database_url` accessor 自動做這 4 處 transform（regex 或 urlparse 重組），讓 user 可直接貼 Neon dashboard 原 URL。對應 handoff line "alembic psycopg2 import error 修（roadmap R2 prerequisite）"。Deploy 過程實證（2026-05-18 第 4 次 redeploy 才成功）：4 處 transform 缺一不可。

### Build Findings (resolved during this spec impl)

實作 plan 時本機 docker smoke 抓到的 Phase 4.1 22-task 遺留問題，已在本 deploy series commit 中修正。記錄於此供未來檢視 module boundary / 分組規範時參考：

- **`uv sync` 階段 ordering** — 初版 Dockerfile 把 `uv sync --frozen --no-dev` 放在 `COPY src/` 之前，hatchling 找不到 source 進行 wheel build → 只裝 deps、專案本身（`bfx-funding-bot-py`）沒裝 → container `bfx-shadow` 啟動 `ModuleNotFoundError: bfx_funding_bot`。Fix（commit `fdee1ad`）：兩階段 `uv sync` — 先 `--no-install-project` 裝 deps（cache layer），COPY src 後再 sync 一次裝專案。
- **`pyproject.toml` runtime vs dev 分組錯誤** — `numpy` 與 `pandas` 原放在 `[dependency-groups] dev`，但 `modules.backtest.strategies.rate_percentile` 在 daemon 路徑（`signal_engine → divergence_reporter → strategy_registry → rate_percentile`）import numpy → container `--no-dev` 時炸 `ModuleNotFoundError: numpy`。`backtest.eda` 也 import pandas 且在 wheel tree 內。Fix（commit `34132a7`）：移到 `[project] dependencies`。

  **隱含 module boundary 問題**：`modules/backtest/` 同時提供 backtest（離線 EDA / WFO）與 strategy class（給 marketfeed runtime 用）。Phase 4.2 brainstorm 時應檢視是否把 strategy class 抽到獨立 module（如 `modules/strategies/`），讓 `backtest/` 真正只服務離線分析路徑。
