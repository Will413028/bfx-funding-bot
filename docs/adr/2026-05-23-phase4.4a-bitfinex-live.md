# Bitfinex live infrastructure — hexagonal split + event-sourcing baseline (Phase 4.4a)

## Context

Phase 4.3 ship `_LedgerWrappedExecutor` → middleware chain + DomainEventBus + 雙 counter ledger（見 [2026-05-22-phase4.3-executor-middleware](2026-05-22-phase4.3-executor-middleware.md)）。下一步要把 BitfinexLiveExecutor 與 WS user channel 接上，但 4.4 整包（infra wiring + live cutover）一次 ship 太大且 verify 不出 layer-by-layer 邊界。Prior state：`modules/execution/` 既有 EchoPaperExecutor / fill_tracker stub / cid 工具混在 domain core 內，4.4 多 venue I/O 進來會把 layering 弄糊。

## Options Considered

### Phase 拆分
- **A. Single 4.4** — infra + cutover 一鍋 ship；簡單但 verify boundary 不清
- **B. 2-phase split：4.4a infra (paper-preserving) + 4.4b cutover**
- **C. 3-phase split：infra / WS dry-run / cutover** — over-engineering，dry-run 跟 cutover 沒實質差異

### WS 架構
- **1. Single WS handler 直接 push to bus** — quick；但 venue I/O + domain mapping + projection 全揉一起，N venue rewrite
- **2. WS + Lookup table** — handler 內查 lookup；OOO race 沒 staging
- **3. Stripe/DDD projection — 4-module SRP split**（auth_ws / ws_dispatcher / live_executor / OfferRegistry）

### Safety net 哲學
- **A. WS-only** — simple；dropout 漏 _reserved 永不釋放
- **B. WS-primary + REST fill_tracker fallback** — 對 idempotency 沒 explicit invariant
- **B+. WS-primary + REST fallback + FSM projection + venue-issued idempotency + replay-from-axiom**（Stripe-grade event-sourcing）
- **C. CQRS open-orders-book + position-book 雙 stream** — over-engineering pre-prod

### Test strategy
- **A. Real Bitfinex testnet** — Bitfinex 沒 testnet
- **B. VCR-replay 真 API trace** — 抓 trace 要先有真 key + 跑 live submit
- **C. Pure mock + fake aiohttp/websockets WS server** — 4.4a paper-preserving 拿不到 fcn 真事件；E2E 推 4.4b

## Decision

7 個原 spec decisions 壓成 4 軸：

- **D1 = 原 spec D1**: 選 **B (2-phase split)** — 4.4a infra ship 後 paper deploy 驗 wiring 不開 ws_client；4.4b 切 BFX_EXECUTOR=bitfinex_live
- **D2 = 原 spec D2/D3**: 選 **WS 3 + safety net B+** — `external/bitfinex/{auth_ws, ws_dispatcher, live_executor}` + `modules/execution/registry_offers.py` (OfferRegistry FSM projection) 四模組分工；fill_tracker 改 registry-aware
- **D3 = 原 spec D4**: 選 **C (pure mock + fake WS server)** — `aiohttp` 不在 deps 改用 `websockets.serve`；E2E 推 4.4b
- **D4 = 原 spec D5/D6/D7**: **Tier 1 best-practice baked in** — Hexagonal lint rule + Functional core/Imperative shell + Bitemporal events v2 (`occurred_at_ms` + `recorded_at_ms`) + Monotonic `event_seq` + Venue-issued `venue_seq` idempotency + Schema upcaster chain + CancelRequested as first-class event + 5 system properties G1-G5 documented + tested

## Rationale

- **D1**: 2-phase ship-verify 的天然邊界。4.4a 全 task 跑完 paper 模式 deploy + boot smoke + L3 endpoint pass，0 風險 surface 30 個 module-level wiring bug。**不選 A**：一鍋 ship 失敗無法定位是 infra 或 cutover。**不選 C**：dry-run = cutover without flip flag，沒額外 ROI。**代價**：4.4 起點延後（已預估在 backend_architecture）
- **D2**: SRP 拆 4 module 對 SaaS multi-venue 必要 — Kraken / Binance 接入只新增 `external/<venue>/`，domain core 不動；WS-primary + REST fallback 是 Stripe-grade pattern (industry standard for async event ingestion)；FSM projection 讓 cold-start replay deterministic；venue_seq idempotency 把 G1 (exactly-once-effect) 變 invariant 不靠 timestamp-based 模糊 dedup。**不選 WS 1/2**：N venue 重寫；**不選 safety A**：dropout exposure stuck；**不選 C**：CQRS pre-prod over-engineering（雙 store consistency 自己 implement vs. aggregate counter）。**代價**：4 module instead of 1，~2x file count vs. minimal approach
- **D3**: Bitfinex 沒 testnet（已 1.5 年態勢）；E2E 在 paper 階段沒有 real fcn → 只能 fake；fake WS server 用 `websockets.serve`（既有 dep），fixture JSON 從 Bitfinex docs 抄。**代價**：4.4b cutover 第一次跑會 surface mock 沒覆蓋的 wire-level mismatch — 已預期，prework `POST /admin/smoke-test` 是 deploy-time gate
- **D4**: Pre-prod 黃金時機；Schema 從 v1 加 Optional fields cost ≈ 0，prod 後動 schema 要 backfill / breaking。Functional core (pure `transition` / `translate_bfx_event` / `parse_frame` / `build_offer_payload`) 90% test 為 unit fn，shell 是薄 IO 包裝。Bitemporal `occurred_at_ms + recorded_at_ms` 對 audit + late-arriving event reconciliation 必要。G3 deterministic replay 強制 projection path 禁 `uuid4()` / `time.time()` — fill_tracker 既有 `uuid4()` (4.3 來的) 為 known bug，4.4a 必 fix。**代價**：schema v2 + upcaster framework + 5 G-test files，但 hook point 完整保留 Phase 5+ outbox/DLQ / per-tenant ledger / per-credit-id ledger 無痛升級

## Lessons

### Rules

- **R1**: Pre-prod schema evolution decision 黃金時機是 ship-before-prod 那個 sprint。`Rule:` 上線前最後一個 pre-prod refactor 一律考慮「之後改成本」— 加 Optional field cost ≈ 0，prod 後加要 backfill + audit trail breaking。Phase 4.4a 加 bitemporal + venue_seq + event_seq 三組 Optional field，全部 default None backward-compat 0 break，prod 後做要協調 Axiom column add + backfill SQL + replay verify
- **R2**: Subagent dispatch 時 plan placeholder names 必須 explicit translate 成 actual codebase symbols。`Rule:` plan 用 `Ledger` / `handle_*` / `Ledger(...)`，actual 是 `PaperPositionLedger` / `on_*` / `PaperPositionLedger(account_id=...)`。Implementer subagent 無法自己 grep 推測，prompt 須在 Context 段 explicit 列 mapping table。Phase 4.4a T4 / T17 / T21 三次因此踩到（修法：plan 開頭加 `## Codebase Notes` mapping table，dispatch prompt 強調讀此段）
- **R3**: Pure function purity 對 deterministic replay 是 hard invariant 不是 nice-to-have。`Rule:` projection path（OfferRegistry / Ledger handlers / translate_bfx_event）禁 `uuid4()` / `time.time()` / `random` / `datetime.now()`，clock 必須 injected。fill_tracker 既有 `uuid4()` 為 G3 違規 bug（4.3 來的），Phase 4.4a 修在 T17（pull correlation_id from registry instead）— pre-prod 4.4a 修是 0 風險，4.4b 切 live 後 surface 才修要重 replay 整段 event log 驗證
- **R4**: `koyeb instance exec` 需要 TTY — non-TTY context (subagent / CI / script) 跑會 fail。`Rule:` 在 non-TTY 包 `script -q /dev/null koyeb instance exec ...` 偽造 TTY。Phase 4.4a final L3 smoke 踩到，工具 limitation 非 bug

### Observations

- **O1**: Subagent-driven development 對 30-task plan 規模仍 scale — 31 implementer dispatches + ~20 reviewer dispatches 完成 0 unfixable BLOCK；implementer 偶爾 surface plan bug（T10 fcn rate 在 index 12 不是 11 / T29 asyncio backpressure 測試前提錯）並 fix 是 robust signal。Combined review prompt 對 mechanical task (T2/T5/T13/T25/T27/T30) 0 漏 finding 且省半 dispatch，對複雜 task (T17/T19) 仍分開比較踏實
- **O2**: 4.4a paper-preserving deploy 模式（all-new code shipped but env flags default-off）對 Tier 1 best-practice baked in 是 ideal pattern — 30 task 全 ship 進 prod 但 0 behavioral change 直到 4.4b 翻 `BFX_EXECUTOR=bitfinex_live` 才 activate。pre-prod 重構 + ship 解耦的範本，Phase 5+ multi-venue 再用一次
