# Phase 4.1 live 訊號管線 — candle-close 定時觸發、in-process dual-compute、DB warmup + REST gap-fill

## Context

Phase 4 roadmap（[2026-05-18-phase4-staged-rollout-paper-shadow-canary](2026-05-18-phase4-staged-rollout-paper-shadow-canary.md)）的 4.1 要從零蓋 live feed → signal → decision（不下單）路徑：當時 Python backend 只有 REST client、`funding_candles` 表與兩個 backtest 策略，沒有 WS、worker 或 marketfeed。核心要求是 live 算出的訊號必須能跟 Phase 3b backtest 逐筆對齊，否則 G2 的 signal-level match rate 無從量起。

**約束**：

- `external` Bitfinex funding candle 在低活躍時段（凌晨、週末）可能整段沒有成交，下一根 candle 的 WS 事件不會準時到。
- `external` Bitfinex WS 每連線 30 channel 上限；funding candle channel key 依 period_agg 區分。
- `inherited` Phase 3b WFO 結論建立在 1h candle close 上：live 若換 cadence 等於同時換兩個變數；backtest 仍是策略唯一的離線證據，至今成立。
- `inherited` roadmap 已鎖 envelope 與 `signal`／`decision`／`health_check` payload（之後 hosting 換成 Postgres，欄位語意延續）。

## Options Considered

- **基準. Layered services + 只吃已收盤 candle**：Freqtrade 預設 `process_only_new_candles`（https://www.freqtrade.io/en/stable/configuration/）、Hummingbot 的 connector／strategy 分層；本 ADR 大部分選項即採此基準，下列是基準沒回答的子題。
- **Cadence（Q2）**：candle-close（選）／tick-driven／hybrid
- **Observe trigger（Q11）**：time-driven scheduler `mts + timeframe + buffer`（選）／WS 事件驅動／hybrid／partial candle streaming
- **Divergence（Q3/Q4）**：in-process dual-compute code-replay（選）／async batch reconciler／只靠 invariant assertion
- **Warmup（Q8）**：DB 讀 N 根 + REST gap-fill + 之後才 attach WS（選）／WS-only cold start／REST warmup + state checkpoint／純 REST polling
- **WS client（Q10）**：自寫 `websockets` client + 指數 backoff + reconnect 後 gap-fill（選）／官方 `bfxapi` SDK／立即重連／circuit breaker
- **Cell scope（Q7）**：config-driven 全部 3b qualified pairs（選）／只跑預定 canary 那一格
- **下單金額來源（Q12）**：cell config placeholder（選）／`Strategy.decide()` 回傳金額／live wallet × ratio
- **Event persistence（Q9）**：Axiom primary（選，已被取代）／Postgres primary／dual-write

## Decision

- **D1 = Q2+Q11**：策略只在 candle close 後由 per-cell scheduler 於 `mts + timeframe + 5s` 觸發；WS 只負責寫 DB，scheduler 從 DB 讀該根，缺就 emit degraded 並跳過該 tick。
- **D2 = Q3+Q4**：每根 candle 同時跑 live strategy instance 與「從 DB history 重建的新 instance」，比 `signal_score`／`signal_direction`，不一致 emit `signal_divergence`（2026-05-21 從 `signal` + warn 拆成獨立 event_type，避免重複計數）。範圍只做 code-replay；forecast-vs-actual 屬 4.3。
- **D3 = Q8**：startup 先讀 DB 最後 N 根餵 `observe()`，落後超過 1 interval 就 REST gap-fill，完成後才 attach WS；strategy state 不做 checkpoint。
- **D4 = Q10**：自寫 WS client，backoff 1s→60s cap、連線活 ≥5min 重置、reconnect 成功立即 gap-fill 再 resubscribe；只訂 candles channel（Q6）。
- **D5 = Q7**：`cells.yaml` + `BFX_CELLS` override，預設跑全部 11 個 3b qualified pairs（RP×6 + MR×5）。
- **D6 = Q12**：金額不進策略介面，4.1 用 cell config `reference_amount_usdt`（venue 最低下單額）佔位，4.2 換成 cap／wallet。
- **D7 = Q5**：phase 由 `BFX_PHASE` env 決定，單一 daemon code path，G1 驗證外掛 script。
- **D8 = Q9**：`signal`／`decision`／`health_check` 直送 Axiom，4.1 不建 Postgres event 表（已被取代，見 Result）。

## Rationale

- **D1**：G2 要 apples-to-apples，live 與 WFO 同樣吃 1h close。**不選 WS 事件驅動**：低活躍時段下一根 mts 不會來，observe 會卡住；**不選 partial candle**：直接破壞與 backtest 的對齊。**代價**：每 tick 固定晚 buffer 秒反應。
- **D2**：3b 已踩過 `market_rate_source` 兩種接法的 silent divergence；replay 11 cells × 千筆級是毫秒級，所以能每根即時比，而非事後批次對帳。**不選 invariant-only**：抓不到 warmup 少一根這類 silent state 差異。**代價**：每 tick 多一次完整 replay。
- **D3**：RP lookback 168h，WS-only cold start 要 168 小時才熱好，G1 1hr smoke 不可能過；gap-fill 與 reconnect 共用同一 helper；live 與 replay 讀同一批 DB rows 才可能 byte-equal。**不選 checkpoint**：重啟重 warmup 只需秒級，序列化會帶來版本相容問題。
- **D4**：health payload 要的 `reconnect_count_last_hour`／`last_msg_age_ms` 必須由自家 client 主動產生，包 SDK 反而要反向挖資料；**不選 circuit breaker**：4–6 週 canary 不能要求半夜人工介入。**代價**：自維護 ~150 行 WS 協定碼。
- **D5**：多 cell shadow 給 G2 較大樣本，也避免在 shadow 前就預設 canary 那一格；**代價**：shadow 資源與雜訊變多。
- **D6**：rate × period 是 3b 的 ground truth，資金配置屬 4.2 layer；金額塞進 `decide()` 會污染 backtest 介面與歷史 replay。
- **D8**：當時依「log 平台放 diagnostics、relational DB 放 transactional invariants」分層；此分層原則在後續遷移中保留，但 hosting 選擇被推翻。

## Result

- 22-task plan 全部落地，驗證 197 unit + 4 integration + 2 benchmark pass（4.1 Koyeb deploy spec 記錄）；取回：`git log --oneline c36a281^..58fd709`。
- **仍成立（現行）**：D1／D2／D3／D4／D5／D6／D7 的形狀都還在 `backend/ARCHITECTURE.md` §2–§4、§8（scheduler buffer 改成 `BFX_SCHEDULER_BUFFER_S`；warmup 與 replay 在 4.3 統一為 LOCF 重建，見 [2026-05-20-phase4.3-locf-staleness-budget](2026-05-20-phase4.3-locf-staleness-budget.md)；phase 現為 `paper`／`shadow`／`live`；金額改由 deployment reconciler 依 gap 動態決定）。
- **已被取代**：D8 → [2026-05-23-postgres-event-store-sot-migration](2026-05-23-postgres-event-store-sot-migration.md)、[2026-05-25-event-store-3c-axiom-removal](2026-05-25-event-store-3c-axiom-removal.md)；spec 的「daemon 永不主動退出、只 emit health」→ 4.2.0 改 `asyncio.TaskGroup` supervision，sub-task 例外即非零退出（ARCHITECTURE §9）。
- **被推翻的假設**：spec 明列「假設 Bitfinex 不修正歷史 candle」與「buffer 足以等到定稿」；live 實際吃到未定稿 candle，改為 candle 不可變 + `is_final` 才能進 `observe()`（[2026-07-27-candle-immutability-bitemporal](2026-07-27-candle-immutability-bitemporal.md)）。
- **cells.yaml 參數**：spec 要求「照 3b WFO best params 抄」，但 WFO 每窗各選 winner、沒有單一 best 組；此 skew 於 [2026-05-28-strategy-validation-oos-and-deploy-safety](2026-05-28-strategy-validation-oos-and-deploy-safety.md) 修正。

## Revocation Triggers

- 策略改吃 tick／order book 即時訊號（不再只看 candle close）→ 重評 D1／D2。
- Bitfinex WS channel 上限或 funding candle key 格式變動 → 重評 D4／D5。
