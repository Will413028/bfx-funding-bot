# Executor middleware chain + dual-counter ledger (Phase 4.3 architecture)

## Context

Phase 4.2 ship 後 Tier D 5 個 follow-ups 中 M1（`_LedgerWrappedExecutor` 4.4 要分 `"submitted"` vs `"filled"`）最架構性。4.2 EchoPaperExecutor 永遠 return "filled" paper-safe；4.4 BitfinexLive 將 return "submitted" (offer placed, async fill via WS `fcn`)，目前 wrapper 一視同仁加 ledger exposure 會 ghost exposure / cap block 過期 offer。Prior state: `_LedgerWrappedExecutor` inline class 自 4.2 ship 起在 `daemon.py`，承擔 retry / heartbeat / ledger emit 三責。Brainstorm scope-expanded 成完整中介層重構，因 pre-prod 重構成本 ≈ 0 且為 SaaS multi-venue 鋪路。

## Options Considered

### Executor wrapping pattern
- **A. Extend `_LedgerWrappedExecutor`** — 最小 delta，wrapper 同時做 retry + heartbeat + emit 三責
- **B. Two-layer wrapper** — `ReservationEmittingExecutor` + `PaperFillSynthesizer`，SRP 但綁 paper 專名
- **C. Emit 倒灌進 executor 內部** — venue adapter 自己 publish 廢 wrapper，refactor 最大
- **D. Middleware chain + DomainEventBus** — onion middleware (Heartbeat > ReservationEmitting > TransientRetry) + canonical event bus，inner pure I/O

### Cap accounting model
- **a. Single signed net position** — spot trading 用，不模擬 reserved
- **b. Account balance + reserved** — mirror Bitfinex wallet UI（BALANCE_AVAILABLE / RESERVED）
- **c. HFT only-filled** — fill latency sub-ms；funding match 掛分鐘到天不適用
- **d. CQRS open-orders-book + position-book** — 兩 stream 分離，event-sourced

### Event taxonomy
- **i. 新 RESERVATION_CLAIMED + RESERVATION_RELEASED + existing ORDER_FILL** — explicit dispatch，每 event = 1 accounting action
- **ii. Reuse OrderStatusChange** — 省 schema rev，但 replay 必須 inspect `status` 才能 decide reserved- 還 realized+

## Decision

- **D1 = Executor wrapping**: 選 **D (middleware chain + DomainEventBus)**。Onion `HeartbeatMW(ReservationEmittingMW(TransientRetryMW(inner)))` + DomainEventBus 取代 inline ledger emit
- **D2 = Cap accounting**: 選 **b + d 組合**：ledger 拆 `_reserved + _realized` 雙 counter；`current_exposure() = reserved + realized`（AllocationCap）、`realized_exposure() = realized`（4.4 L2 guards 預埋）
- **D3 = Event taxonomy**: 選 **i**：新增 `RESERVATION_CLAIMED` / `RESERVATION_RELEASED` EventType，配既有 `ORDER_FILL`
- **D4 = Scope**: scope-expand 成獨立 phase **4.3.executor-middleware**（而非 fold 進 4.4 prework）

## Rationale

- **D1**: SaaS multi-venue 未來 N 個 executor 共用 retry / heartbeat / emit 邏輯，middleware decouples cross-cutting concerns 與 venue I/O。Approach A 對 1 venue OK，N venue 變 god-wrapper；B 兩 wrapper 共享狀態 ceremony 多；C 把 cross-cutting 倒灌進 adapter，N venue 要 N 次 re-wire。**代價**：~3-4x code volume vs A，但對 4.4 / 5+ 接續 0 refactor 成本
- **D2**: Mirror Bitfinex wallet accounting（user 心智模型對齊）；4.4 L2 guards 需 realized-only 算 drawdown / realized loss，single counter 算這些永遠錯。**不選 a/c**：funding 單方向 + match latency 高，HFT only-filled 會 over-submit；**不選 純 d**：CQRS 兩 store 對單 process pre-prod 是 over-engineering，2-counter aggregate 是合適中間點
- **D3**: 每 event = 1 unambiguous accounting action，replay + query 在 SaaS scale (N tenant × M event/sec × K query/day) 都 cheaper。fill_tracker 4.2 stub 的 coarse `"filled_or_cancelled"` 在 replay 根本無法 decide reserved- 還 realized+，i 直接消滅 ambiguity。**代價**：1 EventType enum 擴 + 2 個 Pydantic payload class
- **D4**: M1 brainstorm surface 真實 scope = executor 中介層 + ledger schema + event taxonomy 三件事，不是 single follow-up。Pre-prod 重構成本 ≈ 0，與其 4.4 邊接邊重構，先打好中介層。**代價**：4.4 起點延後 1-2 天

## Lessons

### Rules

- **R1**: Behavior-preserving refactor 的 verification standard ≠ new feature verification。`Rule:` 若 refactor 保留 public API + observable behavior（如 Phase 4.3 `current_exposure()` 不變），驗證重點是 invariants hold + integration test 過 + deploy boot health，不該背 feature-correctness 的 axiom-row 出現驗收 — 後者跟 phase ladder advancement 走
- **R2**: Pre-prod 「best practice 起點 = future best practice 不需改 API」是關鍵設計原則。`Rule:` 重構決策時優先考慮 hook point 未來能無痛升級到 next-level pattern（bus.publish 預留 outbox/DLQ hook、`_realized: Decimal` 未來 evolve to per-credit dict 但 API 不變）。Pre-prod 改 schema 成本 ≈ 0，prod 後動 schema 要 backfill + audit trail breaking
- **R3**: Subagent prompt 對 git commit step 必須 explicit list intended files。`Rule:` 永遠 `git add <path1> <path2>`，禁 `git add . / -A`。對含 `.env.*-bak` / secret-adjacent repo 風險不對稱（誤 commit local-only 也要 reset + gitignore 補洞，比 explicit list 麻煩多）— Phase 4.3 Task 7 implementer 誤 stage `.env.chaos-bak` 已踩

### Observations

- **O1**: Brainstorm 時 user 主動觸發「什麼是 best practice / 業界怎麼做」是 decision protocol working signal — 要求先攤完整 industry spectrum 再 recommend，不是 challenge recommendation。Phase 4.3 session 3 次連續觸發（architecture / sub-arch / verification scope）說明 architecture-level 議題該主動先攤 spectrum，不等第二次問
- **O2**: Combined spec compliance + code quality review prompt（同一 subagent dispatch，spec 先 code 後）對 mechanical task (Task 5/6/7/9/11/12/13/14) 沒漏 finding 且省一輪 dispatch；對複雜 task (Task 10 daemon rewire) 仍分開以針對性問題
