# Phase 4.2 — 真錢前先建 pre-trade guard chain 與 executor port，只接 paper executor

## Context

4.2.0 daemon 穩定後，4.4 canary 前必須先有真錢防護與 executor 抽象，否則 signal 一接 venue 就沒有任何保險。當時策略 signal 在 tentative 階段就 emit decision event，沒有 guard、沒有 executor 抽象、也沒有 fill 追蹤。

**約束**：

- `external` Bitfinex REST 預算約 30 req/min；funding 成交延遲是小時到天級。
- `external` 代管他人 API key 在多數司法管轄區是受監理業務 → SaaS 多租戶另開 spec。
- `inherited` 4.2.0 的 TaskGroup + Transient/Fatal 分類（[2026-05-18-daemon-supervision-and-paper-smoke-gates](2026-05-18-daemon-supervision-and-paper-smoke-gates.md)）；仍成立：同一個 daemon runtime。
- `inherited` 當時 event sink 是 Axiom（30 天 retention），ledger 只能從它 replay；此約束已於 [2026-05-23-postgres-event-store-sot-migration](2026-05-23-postgres-event-store-sot-migration.md) 解除。

## Options Considered

基準：**SEC Rule 15c3-5 式 pre-trade risk control**——每筆單送出前經一串獨立檢查，任一失敗即擋（IB risk gateway、Hummingbot connector 同形）。

- **Scope**：day-1 就把 live executor 接進 daemon、以 flag 關（Hummingbot／Freqtrade）／ **只做 port + paper adapter，live adapter 物理上不接進 daemon（選用）**
- **Safety 結構**：單一 SafetyController god class ／ **guard chain（middleware 式）+ per-guard heartbeat（選用，即基準）**
- **Kill-switch 層級**：全部 guard 帶保守佔位 threshold 上線 ／ **L1 hard guards 常開 + L2 calibrated guards 寫好但預設關，等資料校準（選用）**
- **Fill 偵測**：WS push ／ **REST polling 30s，atomic（offers 與 credits 都成功才算）（選用）**
- **Paper 保真度**：latency／partial-fill model ／ **echo-only：同 tick 全額成交（選用）**
- **多租戶**：process-per-user ／ 共享 runtime 立即做完 ／ **加 `AccountContext` seam，`account_id="default"` 寫死（選用）**
- **Decision event 時機**：tentative 即 emit、之後補發 ／ **guard 評估後只 emit 一次 FINAL（選用）**

## Decision

- **D1**：`BitfinexLiveExecutor` 不接進 daemon，只有 learning spike script；4.2 只接 `EchoPaperExecutor`，live 與 4.4 canary 一起接。
- **D2**：`SafetyGuardChain`：依序評估、第一個 BLOCK 短路；每個 guard `asyncio.wait_for(2s)`，timeout 或 exception 一律 fail-closed 並發 `safety_trigger`。
- **D3**：L1 hard（ManualKill／AuthHealth／Heartbeat／AllocationCap）常開；L2 calibrated（RealizedLoss／Drawdown／DivergenceRate）預設關、threshold 為 `null`，強制保有 enabled path 測試。
- **D4**：`RestPollingFillTracker` 30s 一輪、atomic poll，任一端失敗整輪放棄不更新 state，連 3 次發 degraded；預設關，且 registry 強制「fill tracker 開啟 ⇒ executor 必為 live」，paper offer id 前綴出現在 tracker 即 raise。
- **D5**：cid = `blake2b(correlation_id + UTC 日期)` 取 int63，日期在 submit 入口取一次；executor 只對 network／timeout／5xx 做 3 次 retry，4xx 不 retry；auth 失敗 → `sys.exit(78)` 且只在頂層入口呼叫，不進自動重啟迴圈。
- **D6**：Paper echo-only；ledger 由 event replay 重建，replay 失敗則 daemon 不啟動（不回退為空 ledger）。
- **D7**：`AccountContext` + envelope `account_id` 預設 `"default"`。
- **D8**：signal engine 先建 tentative decision → guard 評估 → 只 emit 一次 FINAL（POST 或 `SKIP+SAFETY_BLOCK`）。
- **D9**：chaos 測試（rate-limit storm、submit 中途斷網、fill tracker 半邊故障、guard 卡住）寫成規格，排在 4.4 canary 第一週執行，不當 4.2 ship gate。

## Rationale

- **D1**：solo + 真錢 + concept stage，物理隔離比「相信 flag 關著」安全；Hummingbot 類 OSS 選 day-1 接線是為了早收多用戶 issue，本場景不適用。代價：4.4 仍要一次接 live adapter 與 fill tracker。
- **D2/D3**：chain 讓新規則只是註冊一個 guard，不改結構，比 god class 容易拆到多帳戶。L2 預設關而非放保守佔位值，因為佔位 threshold 是已知反模式——編出來的數字永遠不會被校準。代價：4.2 上線時 loss／drawdown 保護實質不存在。
- **D4**：成交延遲以小時計，WS push 沒有 ROI；atomic poll 防止「offers 拿到、credits 失敗」被 diff 成假取消。代價：最多 30s 延遲與固定 REST 預算（4 req／30s）。
- **D5**：FIX ClOrdID／Stripe Idempotency-Key 慣例——同一意圖跨 retry 用同一 id，靠 venue 去重；日期在入口取一次防跨午夜產生第二個 id。auth 失敗自動重啟是 SRE Book ch.22 的反模式，獨立 exit code 區分基礎設施故障。
- **D6**：沒有 ground truth 前不 model latency／partial fill。不選空 ledger 回退：空 ledger 會讓 AllocationCap 放行超額曝險。
- **D7**：20–30 行換 Phase 5 不必改 executor／safety／event schema；process-per-user 撞 Bitfinex 每 IP 連線上限，共享 runtime 現在做是過度設計。
- **D8**：每個 cycle 一個不可變 decision event（event sourcing），相較「先發再補」不會留下互相矛盾的兩筆紀錄。

## Result

```
git log --oneline b7dc8a4^..8b4e72d
```

- 4.2 main ship：7 guards／chain／EchoPaperExecutor／PaperPositionLedger，paper-only gate；整合測試 Path A（happy）、B（block 只出一個 SKIP）、D（fill tracker 兩輪對帳）、E（auth → exit 78，含 subprocess 端到端）。實作中發現 `FundingCredit` 不帶 cid，fill tracker 改以 `venue_offer_id` 為 state key。
- **後續演進（2026-09-27 對照 origin/main）**：D2 fail-closed chain 與 exit code 78 仍在（`backend/ARCHITECTURE.md` §6、§9）。D5 的前提已失效：funding submit 沒有 client cid，改用金額指紋；ambiguous submit 一律 `ReservationUnknown` 且不自動 retry（ARCHITECTURE I-UA）。D6 ledger 改由 PG event store replay。spec CC1「safety_chain／executor heartbeat 在每次 tick 入口打」被 `3092d02` 推翻：它們降為 activity heartbeat，只 WARN。L2 的 loss／drawdown guard 接的是回傳 0 的 stub（見 [2026-05-29-credit-aware-reconcile-v2](2026-05-29-credit-aware-reconcile-v2.md)）。
- D9 chaos C1–C4：repo 內 execution log 空白，亦無其他執行紀錄——視為未執行。

## Followup

- [ ] (決策) D9 chaos 規格是否仍要執行：C2（cid 重用）前提已不存在；C1／C3／C4 需改寫成對 VM 環境與現行 `ReservationUnknown` 語意的版本，否則正式放棄。

## Revocation Triggers

- 接第二個 venue 或多租戶上線 → 重評 D7 seam 是否足夠、guard 是否需 per-account 設定。
- L2 guard 取得真實 PnL 來源 → 依資料校準 threshold 後再逐一開啟，不得先填佔位值。
