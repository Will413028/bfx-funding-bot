# Phase 4.4b prework — live cutover enablers

## Context

[Phase 4.4a](2026-05-23-phase4.4a-bitfinex-live.md) paper-preserving ship 後 Followup 留 4 個 stub / scaffold，本身都不足以單獨開 ADR，但**焦點是同一個 event log + cancel flow**，1 spec / 1 plan / 1 ship 是最小可驗證單位：

1. `_AxiomQueryAdapter` (4.3 stub `daemon.py:548`) returns `[]` → ledger replay 無 recover
2. `_OfferRegistryQueryStub` (4.4a stub `daemon.py:571`) returns `[]` → OfferRegistry replay 無 rebuild
3. `BitfinexLiveExecutor.cancel` 只 publish `CancelRequested` 沒打 REST → live 後 cancel intent 不到 Bitfinex
4. `OfferRegistry._parse_event` 只實作 `RESERVATION_CLAIMED` branch → ORDER_FILL / RESERVATION_RELEASED 無法 replay 重建

Goal：一次 deploy 後翻 `BFX_EXECUTOR=bitfinex_live` + `BFX_WS_CLIENT_ENABLED=true` 兩 flag 即 activate live，**不需** mid-cutover 補 code。

## Options Considered

### D1 — Axiom replay adapter 形狀
- **A. 2 獨立 class 各 inherit base** — nominal subtyping，N protocol 多 N class
- **B. Stripe god EventStore** — 含 smoke method；smoke (3-col projection) vs replay (full payload) 是不同 read model
- **C. 1 class 2 method**（duck-typed satisfy 2 protocols）

### D2 — Cancel event 數
- **A. 1-event (StateChange only)** — lose user-intent
- **B. 2-event (Request + StateChange)** — lose "REST 打到了沒" debug breadcrumb，sad path 5xx 無法 distinguish
- **C. 3-event (Request + Ack + StateChange)** — Stripe / FINRA-style financial audit

### D2.5 — Cancel state mutation owner
- **A. executor.cancel 同步 publish ReservationReleased** — violates Single SoT；ledger dedup `(voi, venue_seq)` REST 沒 venue_seq → over-release
- **B. fill_tracker REST poll 出 ReservationReleased** — cancel latency = poll interval (10-30s)，user-triggered 太慢
- **C. ws_dispatcher only**（4.4a `_translate_foc` 已 ship）

### D3 — `_parse_event` schema bridge
- **A. 一次 schema v2 migration**（Pydantic alias / upcaster chain）— scope creep
- **B. mirror ledger.py:164-182 既有 legacy bridge** — mechanical / consistent

### D4 — Env var (ledger + registry 各自 vs 共用)
- **A. `BFX_LEDGER_REPLAY_DAYS` + `BFX_REGISTRY_REPLAY_DAYS` 分開** — 12-factor 教條，無 ROI
- **B. 改名 `BFX_EVENT_REPLAY_DAYS` 共用** — same event log 同 replay window，operational coherence

## Decision

- **D1 = 原 spec D1**: 選 **C (1 class 2 method)** — `AxiomReplayQueryAdapter` 用 Hexagonal port-per-consumer + duck typing 同時滿足 `ledger._AxiomQueryProtocol` + `registry_offers._AxiomQueryProtocol`
- **D2 = 原 spec D2**: 選 **C (3-event audit)** — 新增 `CancelAcknowledged` event，**audit-only ledger/registry 不訂閱**
- **D2.5 = 原 spec D2.5**: 選 **C (ws_dispatcher only)** — 保留 Single SoT；executor.cancel 不 publish ReservationReleased
- **D3 = 原 spec D3**: 選 **B (mirror legacy)** — ORDER_FILL 用 `offer_id` / `fill_size_usdt` / `fill_price` legacy field name；RESERVATION_RELEASED 用 v2 name
- **D4 = 原 spec D4**: 選 **B (shared rename)** — `_resolve_event_replay_days()` helper 雙讀 transition 1 cycle

## Rationale

- **D1**: Python duck typing > nominal subtyping，1 class 2 method 是慣例。**不選 A**: 重複 httpx pool / aclose；**不選 B**: smoke vs replay genuinely 不同 read model，混入 violates SRP。**代價**：兩個 method 是 duck-typed 巧合對齊，read code 要 cross-reference 兩個 protocol 才看到契約

- **D2 + D2.5**: 4.4a 已 chose Hybrid primary + fallback，ws_dispatcher `_translate_foc` 已含 user_cancel/venue_cancel/expired 三 reason classification + 5s `recent_cancels` window。本 spec 只負責 publish intent + REST ack，**不**自己 publish ReservationReleased。**不選 D2 A/B**: 1/2-event 模型在 sad path (5xx / network) 無法 distinguish。**不選 D2.5 A**: over-release bug；**不選 D2.5 B**: cancel latency 10-30s 太慢。**代價**：happy path 多 1 個 event ~100ms 後 CancelAcknowledged 緊接 CancelRequested 可能 noise

- **D3**: 在這個 sprint 一次 schema v2 migration 是 scope creep（需 Pydantic alias + upcaster + backfill）。Legacy bridge mirror ledger.py 既有 pattern → mechanical / reviewable / consistent。**代價**：ORDER_FILL 跟 RESERVATION_CLAIMED / RESERVATION_RELEASED schema asymmetry 延後到 4.4b followup

- **D4**: 12-factor "separate concerns" 在這沒 ROI — ledger / registry 本質同一 event log 的 replay window。**代價**：deploy 時 Koyeb secret rename，transition 一個 deploy cycle 雙讀兼容

## Lessons

### Rules

- **R1**: **Replace method body 時必驗 caller**。**Why**: T6 改 `_parse_event` 把 RESERVATION_CLAIMED branch 從 hardcoded uppercase `"RESERVATION_CLAIMED"` 改成 `EventType.RESERVATION_CLAIMED.value`（lowercase，因 Axiom emit lowercase）— 此 fix 方向正確但**同時 surface 一個 pre-existing dead branch bug**：`registry_offers.py:228 fetch_events(event_types=["RESERVATION_CLAIMED", ...])` 餵 uppercase 字串 → 修 `_parse_event` 後 unit test pass 但 3 個 integration test 壞（commit `fb51c54` 修）。`Rule:` 重構 case-sensitive 比對 時 grep 整個 codebase 同字串用法，不只看當前 file；spec_compression 模式下 subagent prompt 必須要求跑 integration suite 不只 unit suite

- **R2**: **Subagent plan template 不可信，必驗 codebase reality**。**Why**: T9 plan 給的 `sign_request(body, nonce, ...)` 是 positional，actual 是 keyword-only `def sign_request(*, body, nonce, ...)`；plan 給的 bus subscriber `lambda e: captured.append(e) or asyncio.sleep(0)` 是 non-async 會 crash（bus 用 `await h(event)`）。`Rule:` implementer prompt 必在 "Pre-flight Investigation" 段 explicit 要求 grep 真實 signature（`grep -n "def sign_request"` / `grep -n "def subscribe"`）— Phase 4.4a R2 lesson 講的是「plan placeholder name → actual symbol」mapping，本 ADR 補一條「plan code template → actual signature」差距

- **R3**: **Spec 的 Risk section warning 跟 spec 的 sample code 矛盾，implementer 跟 reviewer 都跟 sample 沒 catch warning** — 必須 cross-check。**Why**: 4.4b spec 在 D1 Risk section 明確寫「Axiom payload flattening risk（4.4 prework lesson `9261f3f`）」並要求 `_query_apl` 驗 raw response 看 `payload` 還是 `payload.X` dot-notation，**但 spec 自己給的 APL sample 用了 `['payload']`** in project clause（line 94 of spec design doc）。Plan template + implementer + spec reviewer + code quality reviewer + final reviewer 全部跟 sample 沒 catch 矛盾，ship 後 deploy 第一次跑就 400。Bug 1 (`03e3486`) 跟 4.4 prework `9261f3f` smoke adapter **完全一樣的坑**。`Rule:` Spec/plan 自我 review 時，必須把 Risk section 的 warning items 跟 sample code 1-by-1 對照 — Risk 說「X 是 known pitfall」但 sample 自己 demo X 用法是極危險的矛盾。Reviewer prompt 加一條 "Risk-vs-sample 矛盾檢查"

- **R4**: **Mock test 完全測不出 Axiom columnar union schema 行為**，只有 real wire 能 surface。**Why**: Bug 2 (`0447e29`) — Axiom dataset 內所有 event types 的 payload field union 成欄位集合，query 任一 row 都 return 所有欄位（其他 event types 的欄位值是 null）。Parser 把 null 也塞進 payload dict → `OrderFillPayload.model_validate` `extra='forbid'` reject 44 fields → daemon crash exit 1。Unit test 用 fake response 不會自動生成 union schema，integration test (`test_offer_registry_replay`) 用 canned adapter return 控制 rows 也不會。**只有 real Axiom round-trip 會 surface**。`Rule:` 涉及 columnar / OLAP storage 的 query adapter，spec acceptance criteria 「real backend 驗證」**必須真跑過至少一次**，不可以用 env-gated SKIP 蓋掉。弄 staging dataset + 在 CI / 開發機 routine 跑 — 否則 spec acceptance 是 fake guarantee

### Observations

- **O1**: **Subagent-driven development 對 14-task plan 規模仍 scale，但 deploy 階段才 surface real-wire bugs**。15 implementer + ~10 reviewer dispatch + 2 hotfix subagent dispatch 完成 0 unfixable BLOCK；4 個 implementer surface bug（T6 case mismatch / T9 sign_request kwargs / Bug 1 APL `['payload']` / Bug 2 union schema null bleed）並 fix。Two-stage review 對 in-scope bugfix 案例（T6 dead-code claim）critical 但對 wire-level reality（Bug 1/2）無能為力 — 全 mock-based test 都 pass，只有 real Axiom 能 catch。**結論**：subagent-driven scale 上限 = test boundary 真實性上限；test 只在 mock 內封閉就 ship 出 mock-shaped 軟體

- **O2**: **Koyeb ERROR 訊息 misleading**。`Hypervisor was unable to start instances and a non-recoverable failure is detected` 看起來是 infra 問題，但真因可能是 instance 啟動後 daemon crash exit 1，Koyeb 看 instance 死掉就標 ERROR。Bug 1 ship 後第一個 deploy 就是這訊息 — 以為是 Koyeb infra 又 retry 一次，redeploy 也 ERROR 才想到看 runtime log 看到真 traceback。`Rule (potential)`：Koyeb deploy ERROR 第一動作就是 grep runtime log（不是 retry），ERROR 訊息只當提示
